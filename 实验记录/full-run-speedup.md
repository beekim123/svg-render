## 改法（按省的时间排）

### 1. 实验 1 只再出一遍（省约 75 分钟）

需求原话是"全部素材的冻结图完整出两遍（第二遍关掉缓存，换新的 Chrome 进程）"。正式参照就是第一遍，只需要再关缓存、开新进程出一遍，然后和 `out/mac/ref` 逐字节比。
现在是正式参照之外又出了两遍。

改 `tools/ref/audit.mjs` 的 `verifyRepeatability`：完整模式下第一遍直接用 `out/mac/ref`。快速模式保持不变，还是出两遍。

### 2. GPU 遍和重复遍只出冻结图（这两遍各省约 35%）

这两遍只用到冻结 PNG。活图截图、冻结对活图比对、值表、指令记录、`.svg` 和 `.json` 都没人读。

给 `runBatch` 和 `render` 加一个 `frozenOnly` 选项，打开时跳过这些步骤。
活图页上的 seek 和 `__ref.freeze()` 要照常做，冻结 SVG 就是从那里来的，只是不截活图。

复核：挑 3 个素材，打开和关掉这个选项各出一遍，冻结 PNG 要逐字节相同。

### 3. 每个动作、每个倍率只载入一次活图页（每帧省 15% 左右）

现在 `render` 每帧都先调 `prepare`，把整张 SVG 重新载入一遍。`__ref.seek` 是跳到绝对时刻，可以只载入一次，然后按时刻顺序 seek。

探针里 3 个素材、各 6 个时刻，复用页面得到的冻结 SVG 和每帧重载的结果 18/18 字符相同。
但这 3 个都是待机动作，**没测有触发的动作**，也没测往回跳。

做法：先写一个检查，对全部动作只比 `__ref.freeze()` 输出的文字，不截图，几分钟能跑完。全部相同再改。
冻结页还是每帧新载入，不要动，这是实验 1 漏画那个问题的修法。

### 4. 两个 worker（总时间约减半）

全机上限是 2 个耗资源任务、2 个计算 worker，包含其他聊天的子进程和计算线程。确认预算空余时，本任务最多用 2 个 worker。

当前 `SVG_RENDER_JOBS` 只控制 Ninja；实施时要将它接到各遍 `runBatch` 的 `concurrency`，再设置 `SVG_RENDER_JOBS=2`。

### 5. 重复遍能接着跑

重复遍现在是 `cache:false`，中断就得从头再来。
改成每个动作出完写一个完成记录，记下本轮编号。同一轮中断后重跑，跳过已完成的动作。

### 估计

1–3 都做完，单 worker 约 2.5 小时；再开 2 个 worker，约 1.5 小时。

## 什么时候改

1、2、3 都要改 `tools/ref/{batch,index,audit}.mjs`。其中 `index.mjs` 和 `batch.mjs` 在工具指纹里，改了以后正式参照的缓存全部失效。`index.mjs` 还绑着实验 5 的校准凭据，要按 `HANDOFF.md` 的办法重签。

所以：

- 这一轮跑完不要为了提速马上重跑。
- 等下一次本来就要跑全量（比如 Fable 改了判法、工具有修复）时，把提速和那次的修改放在同一个提交里，一起跑一遍。
- 改完先用快速模式（`npm run check`，不加 `--全部`）和 `npm run ref -- --id <素材>` 验证，最后再跑全量。

## 流程上

- **全量只在交验收前跑一次。** 找问题用快速模式和单个素材，几分钟出结果。
- **工具指纹里的文件，攒到一个提交里改。** 改一次就要全部重出，改三次就是三遍全量。
- **性能问题先测再写报告。** 这次报告写了"各环节占比因缺少细粒度计时，原因未查明"。像上面的探针那样，包一层页面方法计时，不改工具代码，10 分钟就能测出来。1 小时规则同样适用：先测，测不出来再交 Claude。
- **数字取到能读的精度。** 写"70 分钟"，不写"4,221,712.378458 毫秒"。
