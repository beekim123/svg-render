## 1 已证实的问题（按严重程度）

### P1 截图会截到没画完的帧（Q1 的真实原因方向）

- **证据**：把两遍的 `scene_hall/待机/2666.6667@2x.png` 逐像素对比，差异聚成 27 个完整的圆形小块（7333.3333 帧是 28 个），每块 5–15 像素宽，正好是一颗尘粒大小。**每一块都是第一遍亮、第二遍暗**。拿同一时刻的正式活图做第三方对照：第一遍和活图在这些块里平均差 1.4–5.8，第二遍差 32–122。正式参照 `out/mac/ref/…` 和第一遍逐字节相同。
- **结论**：第二遍漏画了约 27 颗 `#floating_dust_particles` 里的尘粒，不是边缘抗锯齿抖动，也不是冻结输入不同（冻结 SVG 和值表两遍逐字节相同，这点原报告已证）。
- **线索**：差异块大多集中在 y≈1680–1950 像素的一条横带，另有 1–2 块在右上角。冻结页（已无动画）的指令记录里 `scene_hall` 有 **53 个合成层**（`out/mac/oplog/复杂测试图/scene_hall.json`）。合成层各自分块光栅化，"截图时某层的某几块还没画完"能同时解释"整颗缺失"和"集中在一条带"。
- **代码位置**：`tools/ref/index.mjs` 的 `render`：冻结页乙是整个会话复用的同一个页面，每帧 `setHtml` 换内容后只等两次 `requestAnimationFrame` 就 `Page.captureScreenshot`。两次 rAF 只保证主线程提交，不保证合成线程把所有层的所有块都光栅化完。
- **影响**：8,714 帧"两遍一致"不能证明它们都画完整了——如果两遍都漏了同一处，重复性检查看不出来。这是参照本身的可信度问题，所以排第一。

### P2 冻结时把百分比长度换算错了（Q2 里 fx_circle 的原因）

- **证据**：`fx_circle.svg` 第 208、214 行用 SMIL 动 `<textPath startOffset>`，值是 `0%→100%`。冻结 SVG 里写成了 `startOffset="469.33"`（2750 ms），正好是 91.67% × 512（视口宽）。但 `startOffset` 的百分比按**路径长度**算，外圈路径半径 214、长约 1345。冻结图里内外圈文字因此转错位置；并排图上内圈文字一眼可见错位。
- **代码位置**：`tools/ref/page.mjs` 读 `animVal` 的分支 `if(v.value!==undefined)return v.value`——`SVGLength.value` 会把百分比按视口换成用户单位，丢了单位。
- **为什么"值复核失败 0"没抓到**：复核是在冻结页里用同一个 `animVal.value` 再读一遍，读出来还是 469.33，自己和自己比当然一致。**值复核对"写法丢信息"这类错误是盲的**。
- **范围**：全部素材里带百分比的 SMIL 动画只有这 2 处，所以只有 fx_circle 受影响；但修法要通用（长度一律按原单位写回，用 `valueAsString` 或 `unitType` + `valueInSpecifiedUnits`）。

### P3 文字实验的位置差量错了东西（Q3 的位置部分）

- **证据**：72 条结果里，"最大字符位置差"和字号严格成正比：14px → 5.7，24px → 10.4，48px → 20.3（≈0.42 × 字号），而且同一字号下 plain / spacing / tspan / rotate 完全一样。这不是摆放误差的样子。
- **原因**：`实验/text/page.mjs` 的 `replaceWithPaths` 拿**字形墨迹的紧包围盒**（`getBBox` of path）去比 `getExtentOfChar`。后者是 Chrome 的**字身框**（起点到步进宽、上伸到下伸），本来就比墨迹大一圈。例：48px 的"中"，字身框顶 84，墨迹顶 88.24。
- **需求也有责任**：`docs/阶段0-需求.md` 实验 6 写的就是"每个字的包围盒和 getExtentOfChar 比"，两者口径不同。照第 9 节第 7 条，这类"照做会和 Chrome 实际矛盾"应当先提出来。

### P4 断连后会话不作废，后面全部白等 30 秒超时（Q5）

- **证据**：完整日志第 960637 行起，第一个动作报"Chrome 调试连接已关闭"，后面 8 个动作全是 `Page.getFrameTree` 30 秒超时。
- **代码位置**：`tools/chrome/index.mjs` 的 `connect`：`ws.onclose` 只拒绝了当时挂着的请求，没有标记"已关闭"；之后 `send` 照样往已关闭的 WebSocket 里写——按标准这不报错、直接丢弃，所以每个请求都要等满 30 秒超时。工作进程也不会重开 Chrome。
- **还缺**：没有保存 Chrome 的 stderr 和退出码，所以**为什么断**现在查不出来（崩溃、内存、还是被自己的清理代码关掉）。

### P5 合法空图没有"空"的写法（Q4）

原因清楚，原报告已说明：指令记录要求至少一个画内容的层，空图一个都没有。属于规则缺口，不是 Chrome 问题。

## 2 结论、假设、缺口分开写

| 问题 | 确定的 | 假设（待定向复核） | 还缺的证据 |
|---|---|---|---|
| Q1 重复性 | 第二遍漏画整颗尘粒；第一遍 = 正式参照 = 和活图一致 | 截图时某些合成层的块还没光栅化完 | 同一冻结 SVG 连截 N 次，看会不会偶发缺粒；加上"所有阶段画完再出帧"后是否消失 |
| Q2 fx_circle | 百分比 `startOffset` 写错 | — | 修后重出 fx_circle 一个动作即可 |
| Q2 char_swarm / 3 个 UI | 都是 CSS `transform`/`opacity` 动画；char_swarm 1 倍全部帧稳定在 0.95 左右、2 倍稳定在 0.978，是系统性偏差不是偶发；ui_rule_sign 在翻牌最窄时（scaleX≈0）画面只剩一条细线，相似度的分母极小 | 活图里这些动画在合成线程上跑：先按某个比例光栅成位图，再由合成器缩放/平移，边缘发软；冻结图是直接画的，更锐 | 只重出这几个动作的**活图**，加 `--disable-threaded-animation`（让动画回主线程画），看是否回到 ≥0.95。活图只是辅助，改它的参数不动参照 |
| Q3 文字图像差 | 位置差的量法错（P3）；48px 时 Chrome 文字比轮廓多约 9% 的墨（覆盖率总和 1.09 倍），纵向重心完全一致，横向整体偏 0.7 个用户单位 | Mac 版 Chrome 的网络字体走 CoreText 光栅，会把字形稍微加粗；轮廓走 Skia 路径填充，不加粗 | ①修量法后看真实位置差；②同样的页面加 `-webkit-font-smoothing: antialiased` 再出一份，看墨量差是否消失；③有 Linux 参照的话对一下 Linux（FreeType）是否本来就过 |
| Q4 空图 | 规则缺口 | — | — |
| Q5 断连 | 错误传播有 bug（P4） | 断连原因未知 | Chrome stderr / 退出码 |

## 3 原修复和 160 帧补测可不可信

- **160 帧补测：可信。** 补的正好是 6 个动作（char_swarm 30 + fx_circle 30 + ui_heart 30 + ui_rainbow_slot 两种色各 22 + ui_rule_sign 26 = 160），就是 CPU 自身差那次断连后没跑成的那几个。用的是正式 CPU 冻结图 / 活图和已有 GPU 图，这本来就是需求 4.2 的做法（"CPU 光栅的活图，4.1 已经出了"）。原报告没被改写，"总体通过 = false"写得清楚。
- 顺带一点：4.2 只要求新出 GPU 冻结图，CPU 那份直接用 4.1 的。现在的 `ref:noise` 把 CPU 又全出了一遍，等于多跑一倍，断连也正是出在这多出来的一遍里。以后直接去掉。
- **原 rAF 超时修复和入口停止修复**：从日志和回归记录看说法自洽，我没有重跑，也没逐行审这两处，不给"已确认"。它们不在关键路径上，第二轮全量跑一遍自然会验到。

## 4 修复顺序和最小复核范围

| 顺序 | 做什么 | 复核范围 | 要不要重出参照 |
|---|---|---|---|
| 1 | **P4 断连**：`connect` 记关闭状态，关闭后 `send` 立刻报错；保存 Chrome stderr 和退出码；工作进程遇到断连重开 Chrome、这个动作重试一次，再失败就停 | 加一个回归：跑到一半杀掉自己开的 Chrome 进程，确认几秒内报错并重开（不按名字杀） | 不要 |
| 2 | **Q1 截图时序**定向实验（见下） | 只用 scene_hall 2666.6667@2x 这一张冻结 SVG | 定下做法后，参照版本变了，**要全部重出**（需求 4.1：改参数就等于换参照） |
| 3 | **P2 百分比长度**：长度类 animVal 按原单位写回 | 重出 fx_circle 待机；加一个夹具：百分比 / em / 用户单位的 `startOffset`、`r`、`x` 各一条 | 只 fx_circle，但会并入第 2 步的全量重出 |
| 4 | **P5 空图**：允许"空指令记录"，但要同时满足：冻结图全透明（所有像素 alpha = 0）、没有画内容的层；记录里写明"空图"和这两条证据 | 只这 3 个公开样例 | 不要 |
| 5 | **Q2 其余 5 个动作**：活图加 `--disable-threaded-animation` 重出 | 只这 5 个动作的活图 | 不要。若确认是合成线程造成的，请 Fable 改实验 2 第 2 条的判法（例如活图统一用这个参数出，或细线/极小内容另算），**不是**单纯降阈值 |
| 6 | **P3 文字量法**：比字身框，不比墨迹框。字身框 = 起点 + 步进宽 × 上伸到下伸（按 Chrome 用的字体度量，注意 Chrome 可能把上伸/下伸取整）；再单独比字的起点 | 36 条 2 倍重跑，几分钟 | 不要 |
| 7 | 全量跑一遍 `npm run mac`，**两遍**做实验 1 | 全部 | 是（这就是重出） |

**Q1 定向实验**（约 10 分钟，1 个 worker）：同一张冻结 SVG，

1. 现做法（复用页面乙、两次 rAF 后截图）连截 20 次，记每次 PNG 的哈希和截图时的层树；
2. Chrome 加 `--run-all-compositor-stages-before-draw`（让合成器每帧把光栅等所有阶段做完再出帧，正是为确定性截图准备的）再截 20 次；
3. 每帧新开页面（不复用乙）再截 20 次；
4. 截图后再截一次，两次哈希不同就继续截，直到连续两次相同（"截到稳定为止"，作为兜底）。

看哪种 20/20 一致、而且结果和活图对得上。预期 1 偶发缺粒，2 或 4 稳定。定下来以后把参数写进 `参照版本.json`。

## 6 流程上的问题和改法

### 为什么慢

| 现象 | 数字 | 后果 |
|---|---|---|
| 文书远多于诊断 | 本目录 340 个文件、Markdown 约 10.8 万字；大量"不能写成通过""不代表…"的反复声明 | 时间花在防御性措辞上 |
| 每次改动都靠全量验证 | 全量重复性约 117 分钟；归档 tar 12 GB，`out/` 16 GB | 一个 bug 一轮就是半天 |
| 缺最便宜的诊断动作 | Q1 拿活图做第三方对照、Q2 把失败帧并排看一眼、Q3 看位置差随字号的变化——各几分钟，原报告都没做 | 卡在"机制未知"，只能停下来问 |
| 停下来问用户的都是窄的流程选择 | 需求第 9 节的"先停下来问"被理解成问用户 | 用户成了瓶颈，又看不懂技术细节 |
| 改动不提交 | 45 文件补丁在临时区分大小写卷上，靠 bundle + patch + 指纹恢复 | 审核和续做都要先"考古" |
| 代码压成长行 | 单行最长近 2,000 字符 | 很难审，也很难让别人接手 |
| 多跑了不必要的计算 | `ref:noise` 把 CPU 参照又出一遍 | 时间翻倍，还引入了断连 |

### 改法

1. **分工改成"GPT 写，Claude 查"。** 实现、跑批照旧给 GPT；凡是"结果不对、原因不明"，GPT 最多花 1 小时，然后交一个最小复现（哪个素材、哪一帧、两张图）给 Claude 诊断，不再自己绕圈，也不直接问用户。第 9 节的"先停下来问"改成先问 Claude / Fable，只有真正需要用户拍板的（花钱、下大件、改原件、改验收线）才问用户。
2. **三级验证。** 每个修复先有一个几分钟内跑完的定向复核（单素材 / 单帧）；改完一批再跑"快速模式"（需求第 7 节第 4 项已有）；**全量只在交验收前跑一次**。
3. **文书上限。** 只留需求规定的：`HANDOFF.md`、`验收.json`、每个实验一份记录、`报告/` 下的汇总。不再写"进行中说明""交接草稿""快照""保存核对"；不打 `out/` 的 tar（它能重新生成）。失败照实写一行，不用每处都附声明。
4. **随时提交到 `stage-0`。** 每修好一项就提交，验收以提交号为准。
5. **代码可读。** 加格式化（例如 prettier），一行一句。
6. **需求先改再做。** 本轮暴露的需求问题（实验 6 量法、实验 2 第 2 条判法、截图要等画完、4.2 不重出 CPU）由 Fable 先改进 `docs/阶段0-需求.md`，再交 GPT，避免它按字面做出注定不过的结果。
