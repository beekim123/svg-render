# SVG 渲染工具 · 大致方向

> 给 Fable 5.2 做设计用。2026-11-10 整理。

## 0 请你（Fable）做什么

根据这份方向做**技术设计**。不用写代码，但要具体到 dot 能分阶段照着编码，而且每个阶段都能验收：

3. 分层（缓存）规则和每帧调度；
4. 光栅后端选哪个（第 5 节的候选）；
5. Godot 和 Cocos 怎么接入，各渲染器、各平台的能力分档；
6. 分阶段计划，每个阶段的验收标准；
7. 先做哪些实验，用来证明可行或不可行。

第 7 节列了需要拍板的问题，每个都附了倾向。你可以推翻，但请写理由。

第 3 节的数字都是**数量级粗算**，请当成假设，在设计里给出验证办法。

## 1 起点

- **现在的游戏**：用户有一个哥特画风的卡牌游戏，已经从 H5 移植到 **Godot 4.7.2**，用的是 **Compatibility 渲染器**，规则和 H5 自动对照一致。项目是另一个仓库（`github.com/beekim123/proj-card`）；本仓库 `素材/源文件/现有游戏/` 和 `参考/gemcard-demo/` 里有它的美术和几份参考文件，只当参考，不要改。
- **美术**：源头是 SVG，动画用 CSS `@keyframes` 写。现在的流程是用 Chrome 逐帧导出成 PNG 精灵图集，所以包体很大：
  - 82 个 SVG 共 562 KB，导出成 145 条精灵、3283 帧、约 2.09 亿像素，压成 GPU 纹理是 215 MiB。整个资源包 252 MiB，87% 是纹理；
  - 一只怪的 SVG 35–51 KB，导出后是 1300 万–2600 万像素（12–25 MiB）；
  - 7 个可染色的素材，每个预先烤了 9 种颜色，共 5240 万像素；
  - 后面还有 10 只怪要加进来，照现在的做法包会再涨约 180 MiB。
- **这个工具不按现有素材来设计**。现有素材用到的特性很少（见附录 A），而目标是**画面很丰富、一屏有很多 SVG 也要表现好**。现有游戏只是第一个用户。
- **引擎**：要同时支持 **Godot** 和 **Cocos**（Cocos Creator 3.x）。平台先做 macOS、Windows，后做 Android；Cocos 的网页版可选。
- **实现方式**：用户愿意用 C++ 写原生工具和渲染扩展。不只是调整导入选项，也不是批量把 SVG 提前转成 PNG。

## 2 目标

### 2.1 怎么算"完美表现"

不能定义成和浏览器逐像素一样，Chrome 自己开不开 GPU 光栅画出来都不一样。按下面四条定义：

- **参照**：
  - 固定一个 Chrome 版本（Chrome for Testing，写死版本号）；
  - 固定像素倍率，用 sRGB；
  - CPU 光栅还是 GPU 光栅当参照，请你定。
- **静止帧**：任意时刻冻结的画面和参照比，几项指标要过线。阈值请你定，可以先按下面的起步，再用测试图校准：
  - SSIM ≥ 0.995；
  - 不算抗锯齿边，差值大于 16/255 的像素少于 0.5%。
- **运动中**：缓存重采样会让画面轻微发软，这可以允许，但要有上限（同样用指标定）。超过上限就重画。
- **时间**：每个元素在同一时刻的变换、颜色、透明度等动画值要和 Chrome 算出来的一致。变换误差在 0.01 像素这个量级。

### 2.2 多"丰富"、多"多"

下面是第 3 节粗算用的假设，请你修正：

- **单个素材**：
  - 几百到几千条路径，多层渐变；
  - mask、clipPath、pattern、混合模式、文字；
  - 滤镜：模糊、投影、噪声、置换、光照、颜色矩阵。
- **动画**：
  - 除了变换和透明度，还有颜色、虚线偏移（一笔笔描出来）、路径形变、滤镜参数、遮罩移动；
  - CSS 动画和 SMIL 都要支持。
- **同屏**：
  - 100–300 个实例，30–50 种不同素材；
  - 同一个素材也可能有大量实例；
  - 实例会移动、缩放、旋转、变色。
- **屏幕**：桌面 1920×1080 到 4K，手机 2400×1080。

### 2.3 包体、加载和内存

- 包里存矢量（中间格式），不按帧、按颜色、按倍率展开成位图。
- 不能把包体的成本换成明显的启动卡顿或显存暴涨。首屏和换场景都要有预算。

### 2.4 不做

- SVG 里的脚本、`foreignObject`（嵌 HTML）、外部资源（外链图片、外链字体）、依赖 HTML 布局的 CSS。
- SVG 自带的交互事件（onclick 之类）。如果需要点击检测，由运行时按几何来算。

## 3 粗算（数量级）

### 3.1 场景假设

- 手机屏 260 万像素。
- 同屏 150 个实例、40 种素材，每种平均 800 条路径。
- 所有素材在屏上的面积加起来是屏幕的 3 倍（互相叠着，加上背景）。
- 素材内部平均叠了 4 层。

如果每帧全部重画，每帧要处理约 **3000 万"像素×层"** 和 **12 万条路径**。

### 3.2 四种做法

| 做法 | 每帧成本（粗算） | 结论 |
|---|---|---|
| 每帧全部用 CPU 重画（ThorVG、Skia CPU） | 按每核每秒 1–3 亿像素、每条路径几微秒算：单核几百毫秒，8 核也要几十毫秒 | **不可行** |
| 每帧全部用 GPU 光栅管线重画（三角化、模板缓冲、MSAA，Skia GPU 这一类） | GPU 端：多遍、多重采样，约 1 亿像素等效/帧，60 帧就是每秒约 60 亿像素。桌面独显可以，核显吃紧，手机不行。CPU 端：12 万条路径要准备、提交，不缓存几何的话要几百毫秒 | 几何缓存好、合批做好，桌面才行 |
| 每帧全部用 GPU 计算着色器（Vello 这一类） | 约 200 万段曲线/帧。桌面估计 5–15 毫秒，手机估计慢 10 倍 | 桌面可能行，手机不行；而且前提是有计算着色器 |
| **分层缓存，只重画变形的部分** | 每帧只合成：屏上缓存层的面积加起来约 1600 万像素的贴图填充，60 帧约每秒 10 亿像素。桌面轻松，中端手机可以。只有内容变化时才栅格化 | **唯一到处都可行的做法** |

### 3.3 分层缓存自己的账

- **显存是第一约束**。
  - 屏上的缓存层：1600 万像素 × 4 字节 ≈ 64 MB；缓存画大 1.25 倍约 100 MB；屏外还要留余量。手机大概只能给 64–128 MB。
  - Compatibility 和 WebGL 下，运行时生成的纹理基本只能存成不压缩的 RGBA8。现在的 PNG 图集是压到 1 字节/像素的。
  - 所以必须做到：不动的层合并；模糊、柔和的层用一半或四分之一分辨率存；大背景切瓦片；按显存预算淘汰。
- **会变形的内容才是真正的上限**。
  - 假设 20–30% 的素材有路径形变、颜色、滤镜参数这类动画，它们每帧都要重画：每帧约 600–900 万"像素×层"、3 万条路径。
  - CPU 到不了 60 帧，GPU 光栅管线勉强，GPU 计算着色器在桌面上可以。
  - 所以要有每帧的栅格化预算（毫秒数），超了就降级：降分辨率、降到 30 帧更新，最后的退路是把这一段动画预先烤成帧。
- **首次显示**。
  - 一个丰富的素材约 50 万像素 × 4 层、800 条路径，CPU 栅格化约 10–30 毫秒。首屏有 40 种素材，单核就要 0.4–1.2 秒。
  - 所以要：后台多线程、按场景预热、画完的结果存进磁盘缓存。
- **包体**。
  - 丰富的 SVG 文本每个 50–500 KB。编成二进制（坐标量化、差分、压缩）估计能缩到原来的 1/5–1/10，也就是每个 10–100 KB；500 个素材共 5–50 MB。
  - 如果按帧烤，一个丰富的动画素材至少几十 MB，500 个就是几十 GB，根本装不下。
  - 所以，画面丰富、有动画、素材又多的时候，**包里存矢量是唯一的路**。

### 3.4 由此得出的原则

1. **画一次，用很多次**：不改形状的东西（静态的、只动变换或透明度的、整体染色的）一律缓存，每帧只合成。
2. **只有改形状的才每帧重画**，而且要有预算、能降级。
3. **GPU 矢量光栅是加速手段，不是前提**：有计算着色器的平台用它来扩大每帧能重画的量；没有的平台（Godot Compatibility、WebGL）也照样能跑，只是动态预算小一些。
4. **显存预算决定缓存策略**，不能反过来。

## 4 大方向：架构骨架

```
离线（开发机上）
  SVG（含 CSS、SMIL）
    ├─▶ 前端：固定版本的 Chrome
    │     · 解析、CSS 层叠、单位换算、use/symbol 展开、文字排版信息
    │     · 动画：CSS 动画和 SMIL 的关键帧、时间、缓动（getAnimations 等）；
    │       拿不到结构的，就按时间密集采样
    │     · 输出“解析完的场景”：每个节点的几何、画法、滤镜图、遮罩和裁剪、
    │       时间线，以及哪些参数可以由代码控制
    ├─▶ 编译器：给出分层建议、预处理几何（曲线、包围盒）、量化压缩
    │     → 中间格式（一个素材一个文件）
    └─▶ 参照帧：Chrome 按时间点渲染出来，给对照工具用

运行时内核（C++，不依赖引擎）
  读中间格式（按需读，最好能流式）
  → 时间线求值（变换、颜色、透明度、路径插值、虚线、滤镜参数…）
  → 分层：哪些缓存、哪些每帧重画、哪些合并、哪些降分辨率
  → 光栅后端（可以换）：CPU / GPU 光栅管线 / GPU 计算
  → 滤镜：以 GPU 着色器为主，CPU 兜底
  → 缓存管理：图集、倍率分档、瓦片、按显存预算淘汰、磁盘缓存
  → 调度：每帧栅格化预算、后台线程、预热
  → 输出“合成指令”：四边形或网格 + 纹理 + 变换 + 透明度 + 混合方式 + 裁剪 + 前后顺序

引擎适配层（尽量薄）
  Godot：节点（Node2D / Control）、创建和更新纹理、提交合成指令、和引擎自己的节点排前后
  Cocos：组件（UIRenderer 这一类），其余同上

工具
  对照工具（和 Chrome 参照帧比）、压测场景、素材检查（特性有没有超出支持范围）
```

### 4.1 分层规则（类似浏览器的合成层）

| 情况 | 处理 |
|---|---|
| 静态子树 | 合成一层缓存起来，同一素材的所有实例共用 |
| 只动变换、透明度 | 单独成一层缓存，每帧只改变换。旋转或放大超过阈值，就按新倍率重画 |
| 整体染色、颜色矩阵 | 缓存，在着色器里算 |
| 路径形变、颜色动画、虚线偏移、渐变停靠点动画 | 这一层每帧重画（在预算内） |
| 滤镜 | 内容不变：缓存滤镜的结果，柔和的可以降分辨率。内容或参数在变：每帧用 GPU 做一遍 |
| 遮罩、裁剪在动 | 内容缓存，遮罩单独一层，合成时在着色器里相乘 |
| **混合模式**（multiply、screen、overlay…） | 结果取决于下面画了什么。下面的东西也在动，就不能预先混好。两种办法，请你定规则：一是把一组 SVG 内容先在自己的离屏里合成好（“隔离组”），再整张交给引擎；二是引擎合成时读背景（Godot 的屏幕纹理拷贝，开销大） |
| **组透明度、组滤镜里有各自在动的子层** | 先离屏合成，再整体做透明度或滤镜；每帧一次离屏 |
| 文字 | 字形缓存进图集。排版位置是离线由 Chrome 定，还是运行时用 HarfBuzz 排，请你定 |

## 5 光栅后端的候选

| 候选 | 好处 | 边界和风险 |
|---|---|---|
| **Skia**（锁定在参照 Chrome 用的那个提交） | 最像 Chrome：Chrome 画 SVG 就是 Blink 加 Skia，SVG 滤镜也映射到 Skia 的图像滤镜。CPU、GPU（GL / Vulkan / Metal）都有。文字走各平台的字体后端，和 Chrome 一样 | 编译链重（gn、depot_tools）；每个架构多几 MB 到十几 MB；GPU 模式要和引擎共享 GPU 上下文（见第 6 节），这是最大的风险 |
| ThorVG | 小（几百 KB），MIT 许可，有 CPU、GL、WebGPU 后端；Godot 自己就在用 | 和 Chrome 的差别比 Skia 大；滤镜不全（Godot 4.7.2 自带的只认 feGaussianBlur）；GL 后端成熟度待查 |
| Vello 系（Vello、vello_hybrid、vello_cpu） | Vello 用计算着色器，路径很多时最快；hybrid 版据说没有计算着色器也能跑（待查） | 用 Rust 写；和 Chrome 有多一致未知；滤镜要自己补 |
| Rive 的渲染器（rive-runtime，C++，MIT） | 专门为游戏做的 GPU 矢量渲染器，有多种 GPU 后端 | 它是给 .riv 格式设计的，拿来画 SVG 要做一层转换；和 Chrome 有多一致未知 |
| 引擎原生着色器（自己写：CPU 三角化，着色器算覆盖率和渐变，滤镜用引擎的离屏） | 不用共享 GPU 上下文，Godot 的各个渲染器和 Cocos（包括网页版）都能跑 | 工作量最大；和 Chrome 的一致性要自己一点点追 |

倾向是**用 Skia 当"一致性的锚"**：
- **第一阶段**：只用 Skia 的 CPU 光栅画缓存，画到内存里再上传，完全没有共享 GPU 上下文的风险，先把"画得像"做到位。
- **第二阶段**：再定 GPU 动态层怎么做，是共享上下文用 Skia GPU，还是用引擎原生的计算着色器，由实验结果决定。

## 6 引擎和设备分档

| 档位 | 环境 | 能做什么 | 接入要点 |
|---|---|---|---|
| A | Godot Forward+ / Mobile（Vulkan / Metal / D3D12） | 有 RenderingDevice 和计算着色器，GPU 计算光栅和 GPU 滤镜都能做 | 可以用 RD 自己写计算着色器；也可以让 Skia GPU 通过 `get_driver_resource`、`texture_create_from_extension` 共享设备和纹理，难点是同步 |
| B | Godot Compatibility（GL 3.3 / GLES 3 / WebGL 2） | 没有计算着色器，也没有 RenderingDevice。缓存加合成没问题；动态层只能靠 CPU 或 GL 光栅管线，预算小 | GDExtension 只能用 RenderingServer（纹理、网格、MultiMesh、画布着色器）。公开接口里似乎只有整张纹理更新（待验证）。外来的 GL 调用要放在渲染线程，而且不能打乱 Godot 缓存的 GL 状态 |
| A/B | Cocos 原生（GLES3 / Vulkan / Metal） | 看后端；计算着色器支持到什么程度待查 | 原生插件加自定义渲染组件。Cocos 的 Spine 运行时（C++ 内核 + TS 组件 + 自定义顶点组装）可以当参考。Cocos 的用户常改引擎源码，这条路比 Godot 宽 |
| C | Cocos 网页、小游戏（WebGL） | 只有缓存加合成，动态预算最小 | 内核编成 WASM；包体和内存限制更紧。可选 |

要点：
- 内核不绑定渲染器。运行时按档位决定动态层的预算和降级办法。
- 游戏要不要从 Compatibility 换到 Mobile 渲染器，取决于会变形的内容有多少。请在设计里写出判断条件。
- 尽量不改 Godot 引擎，改了就得每个平台自己编导出模板。Cocos 能不能改引擎，请你评估。

## 7 需要拍板的问题（附倾向）

| # | 问题 | 倾向 |
|---|---|---|
| 1 | 参照 Chrome 用 CPU 光栅还是 GPU 光栅 | CPU，稳定、可重复；GPU 光栅另外抽查 |
| 2 | 光栅内核用什么 | Skia；ThorVG 当小包体的备选 |
| 3 | 动画语义哪些在运行时自己实现（CSS 变换插值、颜色、路径插值、steps 和贝塞尔缓动、SMIL 的 values / keyTimes / calcMode），哪些离线密集采样 | 常见的在运行时实现，冷门的离线采样；两种都要能和 Chrome 逐时刻对照 |
| 4 | 缓存重采样的误差上限、重画阈值、缓存倍率 | 用测试图做实验来定 |
| 5 | 混合模式和隔离组的规则 | 默认把整块 SVG 当一个隔离组，在它自己的离屏里合成。跨素材的混合（比如一个光效素材用 screen 叠到别的素材上）单独支持 |
| 6 | 文字：离线转成路径 / 离线排版加运行时字形 / 运行时排版 | 美术里写死的文字离线排版（位置由 Chrome 定），运行时做字形缓存；代码填进去的文字交给引擎 |
| 7 | 中间格式：一个素材一个文件、按需加载、能不能流式读；坐标量化精度 | 一个素材一个文件，内存映射直接读；量化精度按"放大到 4 倍也看不出来"定 |
| 8 | 显存预算和降级顺序 | 每个档位一个预算。降级顺序：柔和的层降分辨率 → 动态层降帧率 → 动态层降分辨率 → 烤成帧 |
| 9 | 由代码控制的参数：染色、文字槽、显示隐藏、事件（播哪个动作、停住） | 沿用现有游戏的约定（`data-anim` 事件、currentColor 染色、文字槽），推广成一张通用的"参数表" |
| 10 | Godot 先做哪个渲染器 | 先做 Compatibility（游戏现在用的），跑通缓存加合成；GPU 动态层在 Mobile 渲染器上做 |

## 8 验证路线（实验）

先证明能做，再大规模写代码：

1. **一致性**（不用写 C++）
   - 素材：argon 画的复杂测试图，加上公开测试集（resvg 测试集、W3C / WPT 的 SVG 测试，许可证待查）。
   - 做法：每张图按时间冻结成静态帧，和 Chrome 参照帧比。候选是 Skia CPU、ThorVG、resvg。
   - 得出：选哪个光栅内核，哪些特性要自己补。
2. **动画语义**：用 Chrome 提取出的时间线加上自己写的求值器，每 20 毫秒和 Chrome 算出来的值比一次。
3. **缓存的代价**：按层缓存再变换合成，和 Chrome 逐帧画的比。用来定缓存倍率和重画阈值，进而定显存。
4. **性能上限**（需要一个最小原型）
   - 把第 3 节的场景假设做成压测，三组：同一素材大量实例；大量不同素材；会变形素材的比例从 0% 加到 50%。
   - 分别在 Godot Compatibility、Godot Mobile、Cocos 原生上跑。
   - 记录 CPU 和 GPU 的帧时间、绘制调用数、显存、首次显示时间，看谁先到顶。
5. **共享 GPU 上下文**：让 Skia GPU 在 Godot 里（GL 和 Vulkan 各一个）画进引擎纹理，跑一小时不出错、不闪。用来决定 GPU 动态层走 Skia 还是走引擎原生。
6. **包体**：把测试图和现有游戏的 117 个 SVG 都编成中间格式，量大小。

## 11 已知事实 / 推断 / 待验证

- **事实**：
  - 第 1 节和附录 A 的数字，2026-11-10 实测；
  - Godot Compatibility 是 GL 3.3 / GLES 3 / WebGL 2，没有计算着色器，`get_rendering_device()` 返回空；Forward+ 和 Mobile 有 RenderingDevice；
  - Godot 4.7.2 自带 ThorVG，程序字符串里找得到的滤镜名只有 `feGaussianBlur`；
  - Chrome 画 SVG 是 Blink 把 SVG 转成 Skia 的绘制指令，不是用 Skia 的 SVG 模块。
- **推断**：第 3 节的所有数字；Skia 最像 Chrome；各阶段的工作量。
- **待验证**：
  - 各个光栅库和 Chrome 差多少（实验 1）；
  - Godot 整张更新纹理、合批的实际开销；
  - Skia GPU 和 Godot、Cocos 共享 GPU 稳不稳定（实验 5）；
  - Cocos 对计算着色器支持到什么程度；
  - vello_hybrid 在 WebGL 上能不能用；
  - 手机上的填充率和显存上限（实验 4）。

## 附录 A 现有游戏素材盘点（2026-11-10）

- **数量**：117 个 SVG（游戏里 82 个，待接入 35 个），共 885 KB。单个中位数 4 KB，最大 51 KB；形状数中位数 22 个，最多 121 个。
- **用到的特性**：
  - 元素：path、polygon、circle、rect、ellipse、line、polyline、g；
  - 线性渐变、径向渐变、clipPath、静态虚线、currentColor、透明度；
  - 一种做旧颗粒滤镜：feTurbulence → feColorMatrix → feComposite → feBlend multiply，sRGB，用在 7 个文件里。
- **动画**：
  - 只用 CSS `@keyframes`，只动 transform、opacity，另外有一处 `clip-path: inset()`；
  - 缓动有 cubic-bezier、ease-in-out、linear、steps；
  - 47 个文件用了 `transform-box` 和 `transform-origin`。
- **没用到的**：文字、mask、图片、混合模式、模糊、投影、pattern、use/symbol、SMIL、路径形变、颜色动画。
- **游戏代码怎么控制素材**：
  - `data-anim` 事件：播一次后回到待机，或者停在最后；
  - currentColor 染色；
  - 文字槽 `<g>`。
  - 规则见 `素材/源文件/现有游戏/art-manifest.json` 的 `fields`。
