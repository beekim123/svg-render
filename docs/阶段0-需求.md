## 0 一句话

我们要做一个工具，让游戏直接画 SVG，画得和 Chrome 一样。这个阶段**不写渲染器**，只做三件事：

1. 造一把尺子：用固定版本的 Chrome 出"标准答案"（参照帧），再做一个比图的工具；
2. 摸清家底：所有素材用到了哪些 SVG 特性；
3. 做几个实验，证明"用 Skia 照着 Chrome 的指令画"这条路走得通。

## 1 规矩

1. **只读**：仓库里的 `docs/`、`素材/源文件/`、`素材/字体/`、`参考/` 只读，包括测试图。这些是设计文档和美术的原件，要改先问。

### 2.1 两台机器怎么分工

你在 Linux 上开发，用户在 Mac 上验证。**参照和验收以 Mac 为准**，因为游戏跑在 Mac 上，美术也是在 Mac 的 Chrome 里看的。Linux 上的参照只用于日常开发。

| | 你的 Linux | 用户的 Mac |
|---|---|---|
| 谁跑 | 你 | 用户拉 `stage-0` 的代码，跑一条命令 `npm run mac` |
| Chrome | linux64 版，出"Linux 参照"，放 `out/linux/` | mac-arm64 版，出"Mac 参照"，放 `out/mac/` |
| 工具和检查 | 全部工具；第 7 节的全部检查；实验 1、2、3、5、6、7 | 同一套检查和实验 1、2、5、6 再跑一遍 |
| Skia（实验 4） | 编 Linux x86_64 版和 WASM 版 | 编 mac 的 arm64 版和 x86_64 版，量体积 |
| 实验 5 怎么比 | Linux 上我们用 Skia 画的，对 Linux 上 Chrome 的冻结图 | Mac 上我们用 Skia 画的，对 Mac 上 Chrome 的冻结图 |
| 额外的 | | Linux 参照对 Mac 参照的差，每张图四项指标，并进实验 3 |

**`npm run mac` 要做到**：

1. 一条命令跑完，中间不用人操作，不要 `sudo`。
2. 开头先检查要用的东西（Xcode 命令行工具、Node、Python 和它的包），缺什么就打出装它的命令，然后停下。
3. 开头打出这次要下载多少、大概要跑多久。
4. 中断了再跑一次能接着跑，已经下好的、编好的不重做。
5. 结果写进 `报告/mac/`：`验收.json`、实验结果、体积表、Linux 对 Mac 的差、日志，第一行记下跑的是哪个提交。哪一步失败，在最后打出来。
6. 跑完由用户把 `报告/mac/` 提交推送到 `stage-0`，你再拉下来看。

**什么时候请用户跑**：至少两次。第一次是实验 4、5 在 Linux 上有结果以后，越早越好，确认 Mac 上也走得通。第二次是全部做完、准备验收时。要跑的时候直接告诉用户"请在 Mac 上拉 stage-0，跑 `npm run mac`"。

**没在 Mac 上验过的，不能写成验过。** `HANDOFF.md` 里每一项都写明：只在 Linux 上过了，还是两边都过了。

**清单里一个素材长这样**：

```json
{
  "id": "复杂测试图/char_lich",
  "批": "复杂测试图",
  "文件": "…/交回/out/char_lich.svg",
  "动作": [
    { "名字": "待机", "种类": "循环" },
    { "名字": "施法", "种类": "播一次", "毫秒": 1200,
      "触发": { "class": "act-cast" }, "smil": ["#cast_std_anim"] }
  ],
  "染色": false
}
```

- **种类**有四种：`循环`、`播一次`、`播完停住`、`进场后循环`。
- **触发**有两种写法：`{ "class": "act-cast" }`（给根元素加 class）或 `{ "attr": ["data-anim", "hit"] }`（给根元素设属性）。
- **smil**：要调 `beginElement()` 的动画元素。清单里没写时，默认触发文件里所有 `begin="indefinite"` 的动画元素。
- 现有游戏的 `stay` 没说清是"播完停住"还是"进场后循环"。判断办法：把动画定位到进场结束那一刻，看这个状态下还有没有无限循环的动画，有就是"进场后循环"。
- 没有任何动画的素材，只有一个动作"待机"，只出 0 毫秒那一帧。
- **染色**为真的素材（现有游戏里 `tint: true` 的 7 个），出参照时根元素的 `color` 取两种：`#E3263A` 和 `#3FE3F0`，各出一套。

**测试图补充**：argon 正在画一批补充（需求见 `docs/测试图/补充需求.md`：3 个染色图标、`ui_hud_slot`、改 7 个旧图、每张主图一个动作清单 `<id>.json`）。交回验收后会提交进 `素材/源文件/复杂测试图/`，覆盖同名的旧文件。到时候有 `<id>.json` 的素材，以它为准，不用再照 `notes.md` 整理；工具要能重跑，补充进来后把这一批重新出一遍参照。

复杂测试图里有一次性动作的是 4 张（时长照 `docs/测试图/需求.md`）：`char_lich` 施法 1200 毫秒、`char_golem` 受击 400 毫秒、`fx_explosion` 1000 毫秒、`fx_lightning` 600 毫秒。class 名和要触发的动画 id 在 `notes.md` 的汇总表里，写清单前打开 SVG 核对一遍。

**W3C SVG 1.1 测试集和 WPT 这个阶段不接入**，只做一件事：读它们包里自己的许可证文件，把结论写进实验记录（WPT 是 BSD 三条款；W3C 那个查到的说法不一致）。

## 4 工具

### 4.1 参照帧工具（`npm run ref`）

**干什么**：对清单里每个素材的每个动作，在一批时刻上出三样东西。

| 产物 | 位置 | 说明 |
|---|---|---|
| 冻结图 | `out/ref/<id>/<动作>/<毫秒>@<倍率>x.png` | **标准参照** |
| 活图 | `out/live/<id>/<动作>/<毫秒>@<倍率>x.png` | 辅助 |
| 动画值表 | `out/values/<id>/<动作>.json` | 每 20 毫秒一行 |

染色素材的目录名在 `<id>` 后面加 `@<颜色>`。

**Chrome 怎么开**：

```
--headless=new --disable-gpu --force-device-scale-factor=1 --force-color-profile=srgb
--hide-scrollbars --no-first-run --no-default-browser-check --disable-background-networking
--user-data-dir=<临时目录> --remote-debugging-port=0
```

实际用的完整参数写进 `参照版本.json`。以后谁改了参数，就等于换了参照，要全部重出。

开起来以后用调试协议问一次浏览器（`SystemInfo.getInfo`），确认 `rasterization` 是 `disabled_software`，不是就报错退出。

**页面**：起一个本地小服务，提供一个对照页。对照页用 `@font-face` 加载那两个字体文件（字体族名 `Noto Sans CJK SC`，Regular 是 400，Bold 是 700），`html, body { margin: 0; background: transparent }`，SVG 直接内嵌在页面里。

**倍率**：设备倍率永远是 1。把 SVG 根元素的 `width` / `height` 设成 viewBox 宽高乘以倍率。标准出 1 倍和 2 倍。宽度不小于 1920 的大图，2 倍只出 3 个时刻（0、中间、最后）。

**怎么定位到某一刻**（`docs/试验/试验1-冻结取值截图.mjs` 里跑通了，可以参考）：

- CSS 动画：`document.getAnimations()` 拿到的每个动画先 `pause()`，再设 `currentTime`。**自己把动画对象记住**：播完的动画会从 `getAnimations()` 里消失，以后就找不回来了。每个动画记下它开始的全局时刻，定位时 `currentTime = 全局时刻 − 开始时刻`。
- SMIL：`svg.pauseAnimations()`，再 `svg.setCurrentTime(秒)`。
- 触发动作：先定位到触发的那一刻，再给根元素加 class 或设属性，强制算一次样式（读一下 `getBoundingClientRect()`），收集新出现的动画，然后对清单里的 SMIL 元素调 `beginElement()`。
- 动作切换的语义照 Chrome 自己的来：切换后还在的动画接着走，新出现的从 0 开始。**不要**像现有的精灵图导出工具那样把所有动画都重新定位到同一个时间。

**时间表**：一次运行可以按时间表切动作。默认的时间表是：0 毫秒开始待机；待机的参照出完后，在 1000 毫秒那一刻触发下一个动作，每个动作各自从一个新载入的页面开始。另外为 3 个素材（试验图、`char_golem`、`mon_chest`）各加一组"待机播到 1234 毫秒时触发动作"的时间表，检验接着走的动画对不对。

**出哪些时刻**：

| 动作种类 | 冻结图和活图的时刻 | 动画值表的范围 |
|---|---|---|
| 循环 | 一圈里均匀取 12 个，加 3 个按素材 id 定种子的随机时刻 | 一圈 |
| 播一次 | 0；每 50 毫秒一个，超过 24 个就均匀取 24 个；结束前 0.5 毫秒；加 3 个随机时刻 | 0 到结束 |
| 播完停住 | 同上 | 同上 |
| 进场后循环 | 进场那段按"播一次"，循环那段均匀取 8 个 | 进场加一圈 |

"一圈"的长度 = 这个状态下所有无限循环动画（CSS 和 SMIL）的最长周期，最多 8 秒。

**截图**：

- 视口设成 SVG 的显示尺寸（`Emulation.setDeviceMetricsOverride`，设备倍率 1）。
- 背景透明（`Emulation.setDefaultBackgroundColorOverride`，全 0）。
- 等 `document.fonts.ready`，再等两个动画帧，然后 `Page.captureScreenshot`（PNG，裁剪区域是整个 SVG）。
- Chrome 给的 PNG 原样存，不重新编码。
- 每张图旁边放一个同名的 `.json`：素材、动作、时刻、倍率、Chrome 版本、源文件指纹、文字区域（每个 `<text>` 元素在图上的包围盒，对照工具要用）。

**冻结图怎么出**：冻结 = 把这一刻所有动画值写成固定值，去掉动画，让 Chrome 重新画。做法是在活的页面（甲）里读值、生成一份冻结后的 SVG 文本，放到另一个页面（乙，同一个对照页模板）里截图。

写回的规则：

| 动画 | 怎么写回 |
|---|---|
| CSS 动画 | 对每个动画的目标元素、每个被动画的属性：把计算样式里的值写成副本上的行内样式。最后在副本里加一条 `*{animation:none!important;transition:none!important}` |
| SMIL，动的是 CSS 属性（fill、opacity、d、visibility、stroke-dashoffset 等） | 同上，从计算样式读，写成行内样式 |
| SMIL，动的是别的属性 | 从 `animVal` 读，写成副本上的属性。长度、数字、数字列表、点列表、viewBox 直接序列化；变换类（`transform`、`gradientTransform`、`patternTransform`）把列表里各项的矩阵乘起来，写成 `matrix(…)`。注意两个数一组的属性：`stdDeviation`、`baseFrequency`、`radius` 等。`animVal` 的列表是只读的，不能调 `consolidate()` |
| `animateMotion` | 这个节点的局部矩阵 = 父节点的 `getCTM()` 的逆 × 自己的 `getCTM()`，写成副本上的变换 |
| 全部写完后 | 把副本里所有 SMIL 动画元素删掉 |

冻结后的 SVG 文本也存一份（`out/ref/…/<毫秒>.svg`），实验 7 要用。

**动画值表**：

```json
{
  "id": "char_lich", "动作": "施法", "步长毫秒": 20, "时刻": [0, 20, 40],
  "轨": [
    { "节点号": 412, "元素id": "lich_cast_halo", "属性": "transform", "来自": "css",
      "值": ["matrix(…)", "…"], "局部矩阵": [[1,0,0,1,0,0], "…"] },
    { "节点号": 77, "元素id": "glow_blur", "属性": "stdDeviation", "来自": "smil", "值": [[5,5], "…"] }
  ]
}
```

- 一条轨 = 一个被动画的（元素，属性）。CSS 动画从关键帧里拿属性名；SMIL 从动画元素的目标和 `attributeName` 拿；`animateMotion` 记成属性 `motion`。
- 节点号 = 这个元素在原始文档里按先后顺序数到第几个。
- 值：CSS 属性存计算样式给的字符串；`animVal` 类的存数字。凡是会影响位置的轨（transform、motion），另存一份局部矩阵（6 个数，保留 4 位小数）。

**其他要求**：

- 跑过的结果按"源文件指纹 + 工具版本 + 参照版本"缓存，没变就跳过。
- 可以同时开几个 Chrome 并行出图。
- 记录总耗时。

### 4.2 Chrome 自己的差（`npm run ref:noise`）

用同一个工具再出两套图，只出不比，交给 4.3 的工具比：

1. **GPU 光栅的冻结图**：启动参数去掉 `--disable-gpu`，加上 `--enable-gpu-rasterization --ignore-gpu-blocklist`。开起来以后确认 `rasterization` 是开着的，把 GPU 型号记下来。
2. CPU 光栅的活图（4.1 已经出了）。

然后出一份《Chrome 自己的差》报告（`out/报告/自身差/`）：每个素材每个时刻，"CPU 冻结图 对 GPU 冻结图"和"CPU 活图 对 CPU 冻结图"的四项指标，按素材汇总最差值和中位数。Fable 拿这份报告定最终阈值。

本机试过几张，量级供参考：CPU 对 GPU 的相似度在 0.98–0.999；活图对冻结图在 0.96–0.998。

### 4.3 对照工具（`npm run compare`）

**干什么**：比两张图或两个目录，算四项指标，出网页报告，按阈值给通过或不通过。用 Node 写，不要原生依赖。一对 3840×2160 的图 5 秒内比完。

```
npm run compare -- <甲> <乙> --线 静止 --报告 out/报告/<名字>
```

甲、乙是文件或目录（目录按相对路径配对）。`--线` 取 `静止`、`运动`、`GPU`；文字区域自动用"文字"那条线。退出码：全部通过是 0，有不通过是 1，出错（比如尺寸不同、找不到配对）是 2。

**指标的精确定义**（`docs/试验/比较.py` 是试验版，除了第 5 步它都做了，可以拿来对数）：

1. 两张图都读成 RGBA。尺寸不同直接报错。
2. **内容区域** = 任一张图不透明度大于 0 的像素，向外扩 5 像素（方形）。内容像素数为 0 时，四项都按"完全相同"算。
3. 分别叠到深底（三通道都是 32）和浅底（都是 224）上：`颜色 × 不透明度/255 + 底 × (1 − 不透明度/255)`，保留小数。两种底各算一遍后面的指标，取"相似度更低"的那一遍当结果，并记下是哪种底。
4. **相似度**：亮度 = 0.2126 R + 0.7152 G + 0.0722 B。标准 SSIM，11×11 高斯窗，σ = 1.5，窗在图边上用镜像补；C1 = (0.01 × 255)²，C2 = (0.03 × 255)²。结果在内容区域内取平均。
5. **大差像素**：三个通道里差的绝对值最大的那个超过 16，并且在内容区域里。
   **算作边的**：这个像素上，甲的三个通道都落在乙的 3×3 邻域取值范围向两边各放宽 16 之内，**而且**反过来乙也落在甲的范围内。图边上邻域不够的，用边上的值补。
   **大差像素比例** = 不算作边的大差像素数 ÷ 内容像素数。同时也报"连边一起算"的比例，只看不判。
6. **最大差异块**：在"不算作边的大差像素"里，先去掉 1 像素宽的细线（一个像素要保留，必须存在一个包含它的 2×2 小方块，里面 4 个像素全是这类像素），剩下的按八邻域连通，取最大一块的像素数。
7. **平均偏色**：三个通道各自在内容区域里的平均差（甲减乙，带正负号），取绝对值最大的那个。
8. 另报：最大差、平均绝对差。只看不判。

**文字区域**：参照帧旁边的 `.json` 里有文字的包围盒。把这些矩形向外扩 2 像素，里面的像素单独算一组四项指标，用"文字"的线；其余像素算另一组，用 `--线` 指定的线。两组都过才算过。没有文字的图只有一组。

**阈值**（`阈值.json` 的起步值；最大差异块的线按倍率的平方放大）：

| 线 | 相似度 | 大差像素比例 | 最大差异块（1 倍） | 平均偏色 |
|---|---|---|---|---|
| 静止 | ≥ 0.995 | ≤ 0.1% | ≤ 16 | ≤ 1 |
| 文字 | ≥ 0.98 | ≤ 0.5% | ≤ 16 | ≤ 1 |
| 运动，1 倍 | ≥ 0.975 | ≤ 1% | ≤ 32 | ≤ 1.5 |
| 运动，2 倍 | ≥ 0.985 | ≤ 1% | ≤ 32 | ≤ 1.5 |
| GPU | 每张图单独一条线，从《Chrome 自己的差》里读：不能比它差两成以上；保底 0.995 / 0.2% / 16 / 1.5 | | | |

**网页报告**：一个 `index.html`，不依赖外部资源。上面是汇总（多少对、通过多少、每项指标的最差值和中位数）；下面按"最差的在前"排，每一对给：甲、乙、差异图（差放大 8 倍；不算作边的大差像素用醒目的颜色标出来）、四项指标、过没过；点一下能在甲、乙之间来回切。旁边出一份 `结果.json`，内容和网页一致。

**自测**（`npm run check:compare`）：自己生成几对图，结果必须和预期一致。

| 一对图 | 预期 |
|---|---|
| 完全相同 | 相似度 1，其余全 0 |
| 一个带抗锯齿边的实心圆，整体挪 1 像素 | 大差像素比例 = 0；相似度小于 1 |
| 抹掉一个 10×10 的实心方块 | 最大差异块 = 100 |
| 抹掉一条 1×60 的线 | 最大差异块 = 0；不算作边的大差像素 = 60 |
| 每个通道整体加 3 | 平均偏色 = 3；大差像素比例 = 0 |
| 白色半透明块，不透明度 128 对 168 | 至少在一种底上，大差像素比例大于 0 |
| 尺寸不同 | 退出码 2 |
| 一半是文字区域：文字区域里的差只过"文字"线，不过"静止"线 | 通过 |

另外挑 5 对真图，和 `比较.py` 的结果对一下：相似度、平均偏色、连边一起算的大差比例，差不超过 0.001。

### 4.4 特性清单（`npm run scan`）

**干什么**：扫清单里的每个 SVG，列出它用了什么，再对照 `支持范围.json` 分类。在固定版本的 Chrome 里跑（用它的解析结果和计算样式），不要用正则扫文本。

每个文件出一份 JSON，至少有：

- 元素：各种标签的个数；路径的段数合计；嵌套最深几层；
- 画法：纯色、currentColor、两种渐变（有没有焦点偏移、`spreadMethod`、`gradientTransform`）、pattern；
- 描边：虚线、`vector-effect`、`paint-order`、marker；
- 裁剪和遮罩：clipPath（有没有嵌套）、mask（亮度还是透明度）、CSS `clip-path` 的形状种类；
- 混合模式：用了哪几种，各多少处，有没有写在根元素上；
- 滤镜：用了哪些基元，各多少处；`color-interpolation-filters`；被多少个元素引用；
- 文字：字体族、字号范围、有没有 textPath、字间距；
- CSS 动画：动了哪些属性、哪些缓动、有没有负延迟；
- SMIL：哪几种动画元素、动了哪些属性、`calcMode`、`begin` 的写法、`additive` / `accumulate`；
- 不该有的：脚本、foreignObject、外链、`<image>`、`transition`、3D 变换、`:hover`、`@media`。

每一项标上：支持 / 采样兜底 / 不支持 / **没登记**（`支持范围.json` 里没有的，要人来定）。

汇总出一张网页：行是特性，列是素材，格子里是用了几处；"不支持"和"没登记"的单独列在最上面。

### 4.5 Chrome 指令记录（`npm run oplog`）

**干什么**：把 Chrome 画某一帧冻结图时发给 Skia 的绘制指令存下来。阶段 1 要照着这些指令去画。

做法（`试验3-取Chrome指令.mjs` 跑通了）：在页面乙上 `LayerTree.enable`，等 `LayerTree.layerTreeDidChange`，对每个 `drawsContent` 为真的层调 `LayerTree.makeSnapshot`，再 `LayerTree.snapshotCommandLog`。不画内容的层调 `makeSnapshot` 会报错，跳过就行。

- 每个素材出 0 毫秒那一帧的指令（1 倍），存成 `out/oplog/<id>.json`。
- 汇总：每种指令出现在哪些素材里、多少次。
- 已知的限制：渐变和滤镜的内部参数在记录里是空的（只看得到"有一个着色器""有一个图像滤镜"）。
- 另一条路 `chrome.gpuBenchmarking.printToSkPicture()`（启动加 `--enable-gpu-benchmarking --no-sandbox`）本机在无头模式下没写出文件。可以花半天试试有界面模式；成了就能拿到 `.skp` 文件，实验 5 可以直接回放。不成就算了，写进实验记录。

交一份《Blink 对照表（初稿）》：按特性列出 Chrome 用了哪些 Skia 指令、带什么标志。例如本机已经看到的：圆和椭圆用"画椭圆"，矩形用"画矩形"，圆角矩形是带圆锥曲线的路径，带渐变的画笔有"抖动"标志，带滤镜或透明度的组是一个"存层"。

## 5 实验

每个实验在 `实验记录/` 下写一份记录：做了什么、数字、及格没有、遇到的问题。

### 实验 1：参照可重复

全部素材的冻结图完整出两遍（第二遍关掉缓存，换新的 Chrome 进程）。Linux 和 Mac 各做一遍。

**及格线**：同一个平台上，两遍的每一个 PNG 逐字节相同。不要求 Linux 和 Mac 之间逐字节相同。

### 实验 2：冻结正确

对每个出了冻结图的时刻：

1. 在页面乙（已经没有动画）里，按动画值表同样的办法再读一遍那些（元素，属性）的值，和页面甲里读到的比；
2. 冻结图和活图用对照工具比。

**及格线**：值 100% 一致（数字差不超过 0.001）；冻结图对活图的相似度 ≥ 0.95。第 2 条只是防止漏写了哪个属性，不是质量线。

### 实验 3：Chrome 自己的差

就是 4.2，再加一项：**Linux 参照对 Mac 参照**（同一版本的 Chrome，都用 CPU 光栅），每张图四项指标，在 Mac 上由 `npm run mac` 算。**没有及格线，交数字。**

### 实验 4：Skia 试编

1. 取 Skia 的提交 `ca84ce0a6f1659748188469a89361ccea71e3a64`。先自己打开 Chromium 157.0.8103.50 的 DEPS 文件核对这个提交号，对不上以 DEPS 为准，并写进 `参照版本.json`。
2. **编译设置照 Chromium 抄，不用 Skia 自带的默认值。** Chrome 里的 Skia 不是用 Skia 自己的默认设置编的：Chromium 157.0.8103.50 源码里的 `skia/BUILD.gn`、`skia/config/SkUserConfig.h` 和 `skia/config/` 下的其他文件定了一批编译宏和开关，其中有些会改变画出来的像素。做法：
   - 取这个版本标签下的这几个文件，把里面所有的宏定义和影响 Skia 的 gn 设置列成一张表（《Chromium 的 Skia 设置》），每条标上：照抄 / 和我们无关（只影响 GPU、字体、PDF、编解码等关掉的模块）/ 抄不了（依赖 Chromium 自己的代码，写明怎么替代）；
   - "照抄"的全部加进我们的编译（用 Skia 的 `extra_cflags` 或者自己的 `SkUserConfig.h`）；
   - 拿不准某个宏会不会影响 CPU 光栅结果的，按"照抄"处理；
   - 这张表是交付物，阶段 1 的正式编译直接用它。Chrome 升版本时要重做。
3. 在上一步的基础上，只开 CPU 光栅，关掉：两套 GPU 后端（Ganesh、Graphite）、PDF、Skottie、Skia 自带的 SVG 模块、字体后端（FreeType、CoreText、fontconfig）、HarfBuzz、ICU、全部图片编解码。开关的名字以这个提交的 `gn args --list` 为准。`is_official_build=true`。
4. 写一个很小的动态库，里面只有一个导出函数，但要用到以后会用的全部能力：路径和各种图元、描边和虚线、线性和径向渐变、噪声着色器、图片着色器和录制着色器、存层、全部混合模式、路径测量、颜色滤镜（矩阵、查表、亮度）、图像滤镜（模糊、投影、偏移、合并、颜色滤镜、合成、混合、算术、置换、形态学、三种光源的漫反射和镜面光照、矩阵卷积、平铺、裁剪）。链接时去掉没用到的代码，开链接时优化。
5. 你在 Linux 上编 x86_64 版，量动态库大小，记下来供参考。mac 的 arm64 和 x86_64 写成编译脚本，放进 `npm run mac`，在用户的 Mac 上编、量动态库和代码段的大小。脚本要先在 Linux 上把能验的部分验过（参数、宏表、目标文件清单），别等到 Mac 上才发现写错。
6. 同样的内容用 Emscripten 编成 WASM（宏照同一张表），量原始大小、gzip 后、brotli 后的大小。可以参考 Skia 里 CanvasKit 的编译脚本。
7. 交：《Chromium 的 Skia 设置》表、能重复跑的编译脚本、体积表、编译时间、踩到的坑。

**及格线**：mac 两种架构都编得出，动态库每个 ≤ 6 MB（以 Mac 上量的为准）。WASM 压缩后（brotli）≤ 1.5 MB。

mac 超过 6 MB：再找能关的模块。**超过 8 MB 就停下来问。** WASM 超了不挡后面，照实记。

这个实验最多花 3 天。Linux 版 3 天还编不出来，停下来问。

### 实验 5：微场景对照（最重要）

**要回答的问题**：同一个 Skia、照 Chrome 的指令、用 CPU 画，结果是不是和 Chrome 的冻结图一样。整个设计都建立在"是"上面。

手写 8 个小 SVG（每个 256×256 左右），每个再手写一段等价的 C++，直接调 Skia 画到一张 RGBA（预乘、sRGB）的位图上。**链接的 Skia 必须是实验 4 里照 Chromium 的设置编出来的那一份**，不能是默认设置编的。C++ 里调哪些函数、带什么标志，照 4.5 记下来的 Chrome 指令来，记录里看不到的参数（渐变、滤镜内部）去读 Blink 的源码。

| # | 场景 |
|---|---|
| 1 | 纯色路径：凸的、凹的、自己交叉的；两种填充规则；坐标带小数；整体转 17 度 |
| 2 | 矩形、圆角矩形、圆、椭圆、线 |
| 3 | 描边：三种端点、三种拐角、斜接限制、虚线和虚线偏移；不随缩放变粗的描边 |
| 4 | 线性渐变：三种延伸方式、带 `gradientTransform`、多个停靠点、带半透明 |
| 5 | 径向渐变：带焦点偏移 |
| 6 | 组透明度：半透明的组里有互相重叠的子元素 |
| 7 | 高斯模糊（σ 取 0.8、3、12）和投影；滤镜区域把内容裁掉一部分 |
| 8 | 路径裁剪、亮度遮罩、multiply 和 screen 两种混合 |

每个场景出 1 倍、1.5 倍、2 倍，用对照工具和 Chrome 的冻结图比。

**及格线**：每个场景、每个倍率：相似度 ≥ 0.999，大差像素比例 ≤ 0.01%，最大差异块 = 0。

对不上时先查这几样：**Skia 的编译宏和 gn 设置是不是和 Chromium 157 的一致**（对着实验 4 的表逐条核，这一项排第一；另外用默认设置也编一份 Skia 跑同样的场景，把两份结果的差记下来，就知道哪些宏真的影响像素）；Chrome 是不是分块画的（块的边界）；画的时候的倍率和裁剪；渐变的抖动；颜色空间；滤镜的裁剪区域；模糊在 σ 小的时候走的是不是另一条路。查到的原因都写进记录，这些就是阶段 1 的坑。

**有任何一个场景查不出原因、过不了线，停下来问。**

### 实验 6：文字转轮廓

**要回答的问题**：编译时把文字变成字形轮廓，当路径画，和 Chrome 直接画文字差多少。这个实验全在 Chrome 里做，不用写 C++。

1. 写几段 SVG 文字：中文和数字；Regular 和 Bold；14、24、48 像素；带字间距；带 `<tspan dx dy>`；沿圆排的 `<textPath>`；带 `paint-order` 的描边；整体转 15 度。
2. 用 Chrome 的 SVG 文字接口读每个字的位置和转角（`getNumberOfChars`、`getStartPositionOfChar`、`getRotationOfChar`）。
3. 用字形库从那两个 OTF 文件里取每个字的轮廓，转成 `<path>`，按第 2 步的位置和转角摆好，画法（填充、描边、`paint-order`）和原来的文字一样。
4. 两个版本都出 1 倍和 2 倍的冻结图，在文字的包围盒里比。

**及格线**：2 倍下相似度 ≥ 0.98；用轮廓摆出来的每个字的包围盒，和 Chrome 报的字的范围（`getExtentOfChar`）比，位置差 ≤ 0.1 像素。1 倍的数字也交，只看不判。

不及格不用停，照实交数字，Fable 会改方案。
