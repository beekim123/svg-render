### 0.2 我定的主要决定

1. **参照**：固定版本的 Chrome，用 **CPU 光栅**，把动画值写死后再画的"冻结图"当标准。本机试验：同一时刻的截图换进程也逐字节相同。
2. **光栅内核**：**Skia 的 CPU 光栅**，锁在参照 Chrome 用的同一个提交。所有缓存都由它画。ThorVG、Vello、Rive 不用，理由见 5.4。
3. **做法**：照着 Chrome（Blink）给 Skia 发指令的方式去发同样的指令，而不是自己理解 SVG 规范。Chrome 实际发了什么指令，本机试验确认能用调试协议读出来。
4. **分层缓存**：五种层（不变层、移动层、染色层、重画层、离屏组）。同一个素材的所有实例共用缓存。
5. **动画**：常见的在运行时算；编译时每条动画轨都和 Chrome 每 20 毫秒对一次，对不上的自动改成"按时间采样"的轨。
6. **文字**：美术里写死的文字，编译时转成字形轮廓，运行时当普通路径画，**不带字体引擎**。代码填的文字交给引擎。
7. **素材文件**：一个素材一个 `.svgbin`。索引部分读了就能用，几何部分按层按需解码。
8. **GPU 的用法分两步**：先全用 CPU 画缓存（阶段 1–3，哪里都能跑）；再把滤镜和离屏合成放到 GPU（阶段 4）。动态层要不要 GPU 光栅，由压测结果决定，不预先做。
9. **阶段顺序**：把"接进卡牌游戏"提前到阶段 2 之后，因为它只需要缓存加合成。
10. **Godot 不改引擎**，只用 GDExtension。4.7.2 新增的 `DrawableTexture2D` 两种渲染器都有，GPU 部分优先用它，所以卡牌游戏不用为了这个工具换渲染器。

| 结构 | g、defs、use、symbol、嵌套 svg、viewBox、preserveAspectRatio | | switch、a、view、cursor |

## 2 "和 Chrome 一样"怎么量

### 2.1 参照

- **浏览器**：Chrome for Testing **157.0.8103.50**，mac-arm64（2026-11-10 的稳定版）。它用的 Skia 提交是 `ca84ce0a6f1659748188469a89361ccea71e3a64`（从该版本的 DEPS 文件读到，阶段 0 开工时再核对一次）。
- **启动参数**：`--headless=new --disable-gpu --force-device-scale-factor=1 --force-color-profile=srgb --hide-scrollbars`。本机确认 `--disable-gpu` 后 Chrome 报告的光栅方式是"软件"。
- **不用老的无头模式**（chrome-headless-shell），它走的是另一套代码。
- **倍率**：标准是 1 倍和 2 倍两套。做法是设备倍率固定为 1，把 SVG 的 `width` / `height` 设成 viewBox 的 1 倍或 2 倍。抽查 0.5、1.5、3、4 倍。
- **字体**：对照页面用 `@font-face` 从 `素材/字体/` 加载，不依赖系统里装没装。
- **两种截图**：

| 名字 | 怎么来 | 用途 |
|---|---|---|
| **冻结图** | 把这一刻所有动画值写成固定值，关掉动画，再让 Chrome 重新画 | **标准参照**。最清晰，不受 Chrome 自己的合成层影响 |
| **活图** | 动画停在这一刻，直接截 | 辅助：检查"冻结"这一步有没有写错；当"运动中允许发软多少"的标尺 |

为什么要分两种：本机试验 3 看到，Chrome 播动画时会把会动的元素拆成单独的合成层，画一次再变换（和我们的分层缓存是同一个做法）。所以活图本身就带重采样的发软，不能当"清晰"的标准。

### 2.2 四个指标

两张图比之前先做三件事：

1. 都按预乘透明度，各自叠到深底（#202020）和浅底（#E0E0E0）上，两种底各算一遍，取较差的；
2. 只在"有内容的区域"里算：任一张图不透明度大于 0 的像素，向外扩 5 像素；
3. 图边上那一圈像素，邻域取不到的用边上的值补。

| 指标 | 定义 | 防什么 |
|---|---|---|
| **相似度** | SSIM：亮度通道，11×11 高斯窗（σ = 1.5），内容区域内取平均 | 整体画得像不像 |
| **大差像素比例** | 任一通道差超过 16 的像素，去掉"挪 1 像素就能解释"的（甲的值落在乙 3×3 邻域取值范围 ±16 之内，反过来也成立），再除以内容像素数 | 抗锯齿边之外的明显差异 |
| **最大差异块** | 上面那些像素里，去掉 1 像素宽的细线后，连在一起最大的一块有多少像素 | 一个小东西整个画丢，却被比例淹没 |
| **平均偏色** | 三个通道各自的平均差（带正负号），取绝对值最大的 | 整体偏亮、偏暗、偏色 |

"去掉 1 像素宽的细线"是本机试验后加的：Chrome 的 CPU 光栅和 GPU 光栅在图片最底下一行会差出一条 53 像素长、1 像素高的线，那是边界上的抗锯齿差异，不是画错。

`试验/比较.py` 是这套定义的试验版，阶段 0 的对照工具照它做成正式的。

### 2.3 及格线

| 情况 | 相似度 | 大差像素比例 | 最大差异块 | 平均偏色 |
|---|---|---|---|---|
| **静止帧**，CPU 画的缓存，对冻结图 | ≥ 0.995 | ≤ 0.1% | ≤ 16 像素（1 倍时；按倍率平方放大） | ≤ 1 |
| **静止帧里的文字区域** | ≥ 0.98 | ≤ 0.5% | ≤ 16 | ≤ 1 |
| **GPU 算的部分**（阶段 4 的滤镜、离屏合成），对同一帧 CPU 版的结果 | 不比这张图上 Chrome 自己 CPU 对 GPU 的差更差（留两成余量）；保底 0.995 | 同左；保底 0.2% | 同左；保底 16 | 同左；保底 1.5 |
| **运动中**（缓存被变换后重采样） | 1 倍 ≥ 0.975，2 倍 ≥ 0.985 | ≤ 1% | ≤ 32 | ≤ 1.5 |
| **停下来以后** | 0.2 秒内重画，回到静止帧的线 | | | |

这些是起步值。阶段 0 会对全部测试图量出"Chrome 自己的差"（下一小节），我再校一次，写进 `阈值.json`。原则是：**我们和参照的差，不能比 Chrome 自己两种模式之间的差更大。**

方向里起步的"大差像素少于 0.5%"，对 CPU 画的静止帧我收紧到 0.1%：同一个 Skia、同样用 CPU 画，不该有这么多差异；真有，就是指令发错了。GPU 算的部分不能用固定的线，因为 Chrome 自己在带重滤镜的图上 CPU 对 GPU 就能差到 0.5–0.85%（见下表）。

**时间上的及格线**（每个动画值和 Chrome 同一时刻的值比）：

| 值 | 允许的差 |
|---|---|
| 变换矩阵的平移 | 0.02 像素（1 倍时） |
| 变换矩阵的另外四个数 | 0.0002 |
| 颜色、透明度 | 每通道 1/255 |
| 路径坐标、长度（描边宽、虚线偏移） | 0.02 像素 |
| 滤镜参数 | 1% |

## 3 方向第 3 节的粗算：哪些改了

| 方向里的数 | 我的修正 | 为什么 | 怎么验证 |
|---|---|---|---|
| 每帧全部重画：3000 万"像素×层"、12 万条路径，CPU 不可行 | 结论同意。但成本不只看路径数和像素数，**滤镜才是大头** | 噪声（feTurbulence）、光照、置换，每像素的成本是普通填充的 10–100 倍。一个 512×640 的角色套一层 4 阶噪声，CPU 上估计就要 30–60 毫秒 | 阶段 1 的"光栅速度基准"按填充、渐变、各种滤镜分开量 |
| 合成：1600 万像素/帧 | mac 上按 2560×1440 算是约 2200 万像素/帧（屏幕 370 万 × 3 倍面积 × 平均 2 层），60 帧约每秒 13 亿像素 | 屏幕比手机大；手机不在这次范围里。M 系列 GPU 很宽裕，老的 Intel 核显会紧 | 阶段 2 压测记 GPU 帧时间 |
| 显存：屏上缓存 1600 万像素 × 4 字节 ≈ 64 MB | 方向是按实例算的，但**同一素材的实例共用缓存**，显存跟"有多少种素材、背景多大"走，不跟实例数走。按 2560×1440、40 种素材估：背景类约 1100 万像素，其余约 700 万像素，合计约 **70 MB**（缓存倍率 1.0） | 150 个实例里大部分是同几种素材重复出现。真正占显存的是背景，所以省显存的力气要花在背景上：切瓦片、柔和的层降分辨率 | 编译器给每个素材报"估算显存"；阶段 2 压测记实际值 |
| 运行时纹理只能是不压缩的 RGBA8 | 同意，而且先不做运行时压缩 | 压缩（BC / ASTC）会让渐变出色带，过不了 0.995。只染一种色的层可以存成单通道，省四分之三 | 阶段 2 统计各种格式占多少 |
| 会变形的内容：20–30% 的素材，每帧 600–900 万"像素×层" | 按**层**算，不按素材算。一个角色通常只有披风、躯干这几块在变形，不是整个都重画。另外两条能大幅减量：循环的小重画层把一整圈存下来（之后不再画）；同素材的实例分成几组共用。CPU 路线的容量估计是每帧 100–250 万"像素×层"（M3，4 个工作线程，4 毫秒），大约能同时撑住 10–20 个中等大小的变形层 60 帧 | 一只蝙蝠的翅膀 64×48 像素，30 帧一圈才 0.4 MB，200 只蝙蝠共用这一圈，之后零成本 | 阶段 1 量 CPU 光栅速度；阶段 2 压测"变形比例从 0 加到 50%"，记到顶的点 |
| 首次显示：一个丰富素材 10–30 毫秒 | 不带重滤镜时成立；带噪声、光照的要 50–300 毫秒。一个实测的上界：最重的测试图 scene_hall（1920×1080，1.1 万个元素），Chrome 用 CPU 光栅从载入到截出图一共约 0.8 秒（M3，含解析和排版） | 同第一行 | 阶段 1 速度基准；阶段 4 把这类滤镜放到 GPU 上烤（three.js 那个例子证明这样很快） |
| 包体：二进制是 SVG 文本的 1/5–1/10 | **不压缩约 1/4，交给包本身压缩后约 1/6–1/7**；到不了 1/10 | 本机试验 5 拿现有 117 个 SVG 估：885 KB → 约 233 KB（26%）。其中几何只占 68 KB，样式和动画文本反而占了 350 KB。几何再压缩还能减半 | 阶段 1 真编出来量 |
| 包里存矢量是唯一的路 | 同意 | 现有游戏：252 MiB 的资源包里 87% 是纹理；换成 `.svgbin` 后 117 个素材合计不到 0.3 MB，再加 10 只怪也只多约 150 KB，而不是 180 MiB | 阶段 3 接进卡牌游戏后量整包 |

由此，方向 3.4 的四条原则我都保留，补一条：

5. **滤镜能烤就烤，烤的时候尽量用 GPU**。内容和参数都不变的滤镜，结果只算一次；参数在变的，才每帧算。

## 4 总体结构

```
开发机上（离线）
  SVG + 素材清单（动作、染色、槽…）
     │
     ├─▶ 编译器前半（Node + 固定版本的 Chrome）
     │     · 让 Chrome 解析、算样式、展开 use
     │     · 读出每个节点的几何、画法、滤镜、裁剪遮罩、文字的字形位置
     │     · 读出每个动作里有哪些动画（CSS 和 SMIL），并每 20 毫秒记一次动画值
     │     → 场景文件 <id>.scene.json（给人看、给后半用）
     │
     ├─▶ 编译器后半（C++ 命令行，和运行时用同一个内核）
     │     · 动画转成时间线，逐轨和 Chrome 的值对照，对不上的改成采样轨
     │     · 分层，算每层的包围盒、能不能降分辨率
     │     · 用内核自己画一遍，和参照帧对照（自检）
     │     · 坐标量化，写文件
     │     → 素材文件 <id>.svgbin + 编译报告
     │
     └─▶ 参照帧工具（Node + 同一个 Chrome）→ 冻结图、活图、动画值表

运行时内核 svgcore（C++，不认识任何引擎；mac 上是静态库，H5 上是 WASM）
  读 .svgbin → 时间线求值 → 分层决策 → 栅格化任务（工作线程，Skia CPU）
  → 缓存管理（图集、倍率档、瓦片、淘汰）→ 输出两样东西：
       上传指令（哪张纹理、哪一块、像素在哪）
       合成指令（哪张纹理的哪一块，画到哪四个点，什么颜色、什么着色器、什么混合）

接入层（薄）
  Godot：GDExtension。节点 SvgSprite2D；照着指令建纹理、摆四边形
  Cocos H5：组件 SvgSprite；同上

工具
  对照工具、素材检查、压测场景、命令行出图（不经过引擎直接把某一刻画成 PNG）
```

## 5 模块和接口

### 5.1 编译器

**分成两半的原因**：前半必须在 Chrome 里跑（要它的解析和样式结果）；后半要和运行时用同一份求值和光栅代码，这样"编译时自检过了"才等于"运行时画得对"。两半之间用一个 JSON 文件交接，出问题时人能直接打开看。

**前半从 Chrome 里读什么**（定位、触发、读样式和 `animVal`、读矩阵这几项本机试验 1 读通了；currentColor 探测和文字两项还没试，阶段 0 的实验 6 和阶段 1 开头会试）：

| 要什么 | 怎么读 |
|---|---|
| 每个节点的最终样式 | `getComputedStyle` |
| 路径 | 计算样式里的 `d`（Chrome 会给成绝对坐标；CSS 和 SMIL 的形变都反映在这里） |
| 节点的变换 | `getCTM()` 相邻两级相除（这样 `transform-box`、`transform-origin`、沿路径运动都已经算进去） |
| 渐变、pattern、滤镜、裁剪、遮罩 | 读元素属性的 `animVal`，单位让 Chrome 换算好 |
| CSS 动画 | `getAnimations()` 拿关键帧、时长、缓动 |
| SMIL | 读动画元素的属性；用 `pauseAnimations()` + `setCurrentTime()` 定位，再读 `animVal` 或计算样式 |
| 一次性动作 | 加 class 或设属性触发 CSS 动画；`beginElement()` 触发 SMIL。在暂停的时间线上触发也行 |
| 哪些颜色跟着 currentColor 走 | 把根上的 `color` 换两种哨兵色，各读一遍，会跟着变的就是 |
| 文字 | SVG 的文字接口给每个字的位置和转角；字形轮廓从字体文件里取 |

**use 的展开**：Chrome 不让脚本看 use 内部的实例。前半在一份工作副本里把每个 use 换成真的节点，再让 Chrome 算样式。展开前后各截一张图，必须一致，不一致就报错（防选择器在展开后匹配到别处）。后半再把完全相同的子树合并成"共用子图"，所以 3000 个金币不会让文件变大。

**后半的步骤**：

1. 建节点树和资源表；合并相同的子树。
2. 动画转成时间线轨。
3. **时间线自检**：每个动作每 20 毫秒，用内核的求值器算一遍，和前半记下的 Chrome 的值比。超出 2.3 节的差，就把这条轨换成采样轨，并在报告里记一行。
4. 分层（第 6 节）。
5. **静止帧自检**：用内核把每个参照时刻画出来，和冻结图比，四个指标写进报告。
6. 量化、写文件。
7. 出编译报告：文件大小、用到的特性、几层、每层多大、估算显存、哪些轨改成了采样、自检结果。

**素材清单**（每个素材旁边一个 JSON，推广自现有游戏的 `art-manifest.json`）：

```
{
  "id": "char_lich",
  "动作": [
    { "名字": "待机", "种类": "循环" },
    { "名字": "施法", "种类": "播一次", "毫秒": 1200,
      "触发": { "class": "act-cast" }, "smil": ["#halo-anim"] },
    { "名字": "眩晕", "种类": "进场后循环", "毫秒": 600, "触发": { "attr": ["data-anim", "daze"] } }
  ],
  "染色": true,
  "槽": { "dial_text": [160, 210, 28] },
  "开关": { "武器": ["#staff"] },
  "锚点": [256, 620],
  "打击点": [256, 300],
  "最大显示倍率": 4

```

现有游戏的 `events`、`stay`、`tint`、`slots`、`anchor`、`hitPoint` 都能一对一转过来。

### 5.2 素材文件 `.svgbin`

**原则**：

- 一个素材一个文件，小端字节序，所有段 8 字节对齐，段内偏移都相对文件头。
- **索引类的段**（节点表、图层表、时间线索引、包围盒、参数表）是定长记录，映射进内存后直接读，不解析。
- **数据类的段**（路径坐标、关键帧数组）是量化后的变长编码，按层、按需解码；画进缓存后，不变层的解码结果可以丢。
- 文件自己不做通用压缩，交给引擎的包去压（Godot 的 PCK、H5 的传输压缩）。这样才能直接映射。
- 不做网络流式。素材文件都很小（现有游戏最大约 15 KB，测试图里最大的场景估计 0.3–0.9 MB），整个读进来就行；"按需"体现在按层解码。
- 文件是编译产物，不手改。格式主版本变了就全部重编，运行时拒绝读主版本不对的文件。

**段**：

| 段 | 内容 |
|---|---|
| 文件头（64 字节） | 标记 `SVGB`、格式版本、段数、viewBox、默认尺寸、坐标量化步长、源文件指纹、编译器版本、参照 Chrome 版本 |
| 段目录 | 每段的种类、偏移、长度、条数 |
| 字符串表 | 动作名、槽名、开关名、节点 id |
| 节点表 | 种类（组 / 形状 / 共用子图引用 / 槽）、父节点、子树大小、变换号、画法号、描边号、几何号、效果号、所在图层、标志位 |
| 变换表 | 每条 6 个 float32 |
| 画法表 | 纯色（带"跟不跟 currentColor"标志）、线性渐变、径向渐变、pattern |
| 描边表 | 宽度、端点、拐角、斜接限制、虚线 |
| 几何表 | **保留原始种类**：矩形、圆角矩形、椭圆、线、路径；数据偏移、包围盒 |
| 几何数据 | 量化坐标的差分变长整数；命令每条 3 位 |
| 效果表 | 透明度、混合模式、裁剪、遮罩、滤镜（滤镜是一张小图：每个节点一种基元加参数） |
| 共用子图表 | 根节点、包围盒 |
| 图层表 | 种类、包含哪些节点、父层、各动作下的包围盒、缓存提示（能不能降分辨率、是不是不透明、能不能存单通道）、染色方式 |
| 时间线 | 动作表、轨道表（目标、属性、时长、延迟、次数、方向、填充）、关键帧（时刻、缓动、值）、缓动表 |
| 参数表 | 色槽、开关、槽、锚点、打击点、点击区 |
| 自检摘要（可去掉） | 编译时的对照结果，给工具看 |

"保留原始种类"是本机试验 3 得来的：Chrome 画圆用的是 Skia 的"画椭圆"，画矩形用"画矩形"，圆角矩形是带圆锥曲线的路径，渐变还带抖动标志。这些走的是 Skia 里不同的代码，统一转成通用路径就会和 Chrome 差一点。

**量化精度**：

- 默认步长是 1/64 个用户单位，最大误差 1/128 单位。放大 4 倍时误差约 0.03 像素，边上的覆盖率最多差 3%（约 8/255），在 16 的线以内。
- 素材清单里"最大显示倍率"超过 4 的，编译器自动把步长再减半。
- 动画值（变换、颜色、关键帧时刻）用 float32，不量化。

**大小**：现有 117 个素材估算合计约 233 KB（见第 3 节）。真数字阶段 1 量。

### 5.3 运行时内核 `svgcore`

不依赖任何引擎。对外的接口如下（这是设计层面的接口清单，不是代码）：

```
素材
  load_asset(字节, 长度) → 素材号        调用方保证这块内存一直在
  unload_asset(素材号)
  asset_info(素材号) → 尺寸、动作表、色槽、槽、开关、估算显存

实例
  create_instance(素材号) → 实例号
  destroy_instance(实例号)
  set_transform(实例号, 6 个数)          实例坐标 → 画布坐标
  set_order(实例号, 排序键)              前后顺序由接入层给
  set_opacity / set_visible
  set_blend(实例号, 普通 | 相加 | 相乘 | 滤色)   整个素材怎么叠到场景上
  set_color(实例号, 色槽, 颜色)
  set_switch(实例号, 开关名, 开或关)
  play(实例号, 动作名, 起始毫秒 = 0)
  stop / pause / seek(毫秒) / set_speed
  slot_matrix(实例号, 槽名) → 6 个数
  is_ready(实例号) / bounds(实例号) / hit_test(实例号, x, y) → 点击区名

每帧
  begin_frame(当前秒数, 视口, 设备倍率)
  update()                              求值、分层决策、派任务、收结果
  take_uploads(预算字节) → 上传指令[]
  take_draws() → 合成指令[]             已按前后顺序排好
  end_frame()

预热、预算、统计
  prewarm(素材号[], 倍率, 动作名[]) → 预热号；prewarm_progress(预热号)
  set_budget({ 显存, 每帧栅格化毫秒, 每帧上传字节, 工作线程数 })
  stats() → 缓存占用、命中率、每帧栅格化的像素和路径数、降级级别和次数
  回调：动作播完、素材备好、降级级别变了

接入层要实现的
  create_texture(宽, 高, RGBA8 或 单通道) → 纹理号；destroy_texture(纹理号)
  能力表：能不能局部上传、最大纹理边长、有没有离屏通道、能不能自定混合因子、能开几个工作线程
  （阶段 4）run_pass(通道种类, 输入纹理 ≤ 4 张, 输出纹理, 区域, 参数)
  （可选）磁盘缓存的读写
```

**合成指令**的字段：纹理号、纹理上的矩形、画到画布上的 4 个点、颜色乘数（预乘）、着色器种类、着色器参数、混合方式、排序键、属于哪个实例。

**着色器种类**一共六种，每个引擎各写一份，内核只给编号和参数：

| 种类 | 干什么 |
|---|---|
| 普通 | 预乘透明度的贴图 |
| 单色染色 | 单通道贴图 × 一个颜色 |
| 双图染色 | 两张贴图按颜色插值（见 6.3） |
| 遮罩相乘 | 内容贴图 × 遮罩贴图的透明度 |
| 矩形裁剪 | 普通，加一个素材坐标里的裁剪矩形 |
| 颜色矩阵 | 普通，再乘一个 4×5 矩阵 |

**动作的语义**（照 Chrome 的实际行为）：

- 切到一个动作时，新出现的动画从 0 开始；两边都有的动画（比如另一个部件上的待机）**不重来，接着走**；不再生效的动画停掉。
- 动作结束回到待机时，被它顶掉的待机动画从 0 重新开始（Chrome 就是这样，因为那是一个新的动画对象）。
- 现有的精灵图导出工具把每个动作的所有动画都从 0 开始，是精灵图做法的近似。新运行时照 Chrome 的来，会更对。
- 参照帧工具支持"时间表"（比如 0 毫秒待机，1234 毫秒切到受击），这样切换过程也能逐时刻对照。

**线程**：`update()` 在主线程。栅格化在工作线程（mac 上内核自己开线程池；H5 上由接入层开 Web Worker，每个 Worker 里一份只负责栅格化的内核，不需要 SharedArrayBuffer）。

**时间线是确定的**，所以调度可以**提前一帧**把重画层下一帧的内容画好，上屏没有延迟。只有突然切动作的那一帧来不及，沿用上一张图一帧。

### 5.4 光栅后端：Skia 的 CPU 光栅

**决定**：Skia，只开 CPU 部分，版本锁在参照 Chrome 用的那个提交，**编译宏和 gn 设置照 Chromium 同一版本的 `skia/BUILD.gn` 和 `skia/config/` 抄**，不用 Skia 自带的默认值（Chrome 里的 Skia 是带着一批自己的宏编的，有些会改变像素；具体有哪些我还没逐条读，由实验 4 列成表）。升级时 Chrome、Skia、这张设置表一起升，全量重跑对照。

**为什么是它**：

1. **和 Chrome 的一致性是"造出来就有"，不用一项项追。** Chrome 画 SVG 就是 Blink 给 Skia 发指令。同一个 Skia、同样的指令、同样用 CPU 光栅，抗锯齿、渐变、模糊、所有滤镜的算法都是同一份代码。我们要做对的只剩"发的指令和 Blink 一样"，而 Blink 发了什么可以直接读出来对照（本机试验 3）。
2. **滤镜只有它齐。** 光照、噪声、置换、形态学、卷积这些滤镜，Skia 里都有，是为 Chrome 写的。别的库要么没有，要么是另一套实现。
3. **没有共享 GPU 的风险。** 画进内存再上传，哪个引擎、哪个渲染器、H5 都一样。
4. **体积够。** 公开数据：Skia m157 关掉 GPU 后代码段约 5.5 MB（还带着字体等我们不要的模块）。我们不要字体引擎、图片解码、PDF、它自带的 SVG 模块，估计 3–5 MB。阶段 0 试编量准。
5. **能编成 WASM。** CanvasKit 就是 Skia 的 WASM 版，可行性不用证明，只要量体积和速度。在 H5 上用它，各家浏览器画出来的缓存是一样的。

**别的候选为什么不用**：

| 候选 | 不用的理由 |
|---|---|
| ThorVG | 1.0 的 SVG 滤镜仍然只有高斯模糊（2026-11 的提交记录还是这样）。测试图需要的滤镜它大半没有，都得自己写，那就失去了"小"的意义。方向里"当小包体的备选"我去掉了：你给的上限是 10 MB，不需要备选 |
| Vello 系 | 用 Rust；计算着色器那一版 H5 用不了；不用计算着色器的那一版（原名 vello_hybrid，现在叫 vello_gpu）WebGL2 能跑，但官方自己评价还是"大致 beta"，功能比 CPU 版少，没有 SVG 滤镜 |
| Rive 渲染器 | 是给 .riv 设计的；在 WebGL2 上实际走的是多重采样的退路，抗锯齿和 Chrome 差得远；没有 SVG 滤镜 |
| resvg | 只做静态 SVG，用 Rust，只有 CPU。但它是个好**对照物**：阶段 0 可以顺手拿它画同一批冻结图，看"别的库离 Chrome 多远" |
| 自己写着色器光栅 | 工作量最大，一致性要一点点追。只在阶段 4"动态层要不要上 GPU"时作为候选之一 |
| H5 上直接用浏览器自带的 SVG 光栅 | 零体积，但 Safari、Firefox 画得和 Chrome 不一样，违背"和 Chrome 一样" |

**GPU 在哪里用**（不属于光栅后端，但放这里说清）：

- 合成：一直是引擎的 GPU 在做（贴图四边形）。
- 滤镜、离屏合成：阶段 4 放到 GPU，用引擎自己的离屏能力和我们写的少量着色器。这部分的结果和 CPU 版对照，线见 2.3。
- 动态层的光栅：先不上 GPU。阶段 2 压测如果证明 CPU 路线不够，阶段 4 再从三条路里选（见 `阶段计划.md` 的实验 14）。

**字体**：Skia 编译时不带任何字体后端。文字在编译时已经变成轮廓。

### 5.5 接入层

#### Godot（4.7.2，GDExtension，不改引擎）

本机从 4.7.2 导出的接口文档核实过的事：

| 事 | 结论 |
|---|---|
| 纹理更新 | 公开接口只有整张更新：`RenderingServer.texture_2d_update(纹理, 图, 层)`。**没有局部更新** |
| GPU 上画进纹理的某一块 | 有。4.7 新增 `DrawableTexture2D` / `RenderingServer.texture_drawable_blit_rect`：最多 4 张来源纹理、4 个输出，可带自定义的 `texture_blit` 着色器。Compatibility 和 Forward+ 都实现了 |
| 每个画布项单独的着色器参数 | 有：`canvas_item_set_instance_shader_parameter`，不打断合批 |
| 在渲染线程上跑代码 | 有：`call_on_render_thread` |
| 拿底层 GPU 对象 | 有：`RenderingDevice.get_driver_resource`、`texture_create_from_extension`、`texture_get_native_handle`（Compatibility 下没有 RenderingDevice） |
| 2D 合批 | Compatibility 从 4.0 就有；Forward+ / Mobile 从 4.4 起有。换纹理、换材质会断批 |

**怎么接**：

- **类**：`SvgAsset`（资源，装着 `.svgbin` 的字节）、`SvgSprite2D`（节点）、`SvgServer`（单例：预算、预热、统计）。
- **每层一个画布项**。缓存纹理或位置变了才重建它的绘制命令；每帧只调 `canvas_item_set_transform`、`set_modulate` 和实例着色器参数。不变层每帧零调用。
- **一个素材里有很多小移动层时**（一群蝙蝠、几百粒灰尘），改用一个 MultiMesh，每帧只传一次缓冲。用哪种由实验 10 的数字定。
- **纹理**：小层进图集页（1024×1024）；大层用独立纹理；重画层各用一张正好大小的独立纹理，每帧整张更新，不存在"局部更新"的问题。运行中零散新增的小层先进 512×512 的小页，整页重传也便宜。
- **槽**：槽在图层序列里占一个位置。引擎的文字节点挂在槽上，就画在槽前后两段图层之间，和 H5 里把文字插进 SVG 的前后关系一致。
- **素材出框的裁剪**：Chrome 会把超出 viewBox 的内容裁掉。实例可能被旋转，不能用屏幕对齐的裁剪框，所以用"矩形裁剪"着色器在素材坐标里裁。只给编译时算出来会出框的层开。
- **跨素材的混合**：相加和相乘 Godot 的画布着色器直接有。滤色（screen）没有现成的混合因子，画两遍：第一遍用相乘画（1 − 源），第二遍用相加画源，结果就是滤色。
- **颜色**：2D 不要开 HDR（`rendering/viewport/hdr_2d`）。开了以后混合在线性空间里做，和 Chrome 不一样。
- **每帧的入口**：接 `RenderingServer.frame_pre_draw`，保证游戏逻辑这一帧设的位置都已经到位。

**游戏要不要从 Compatibility 换到 Mobile 渲染器**：按这个设计**不用换**。缓存加合成两边一样；阶段 4 的 GPU 部分走 DrawableTexture，两边都有。只有下面两种情况才需要换，到时候我会拿数字来找你：

1. 实验 10 量出来，Compatibility 下整张上传或合成的开销过不了线，而 Mobile 过得了；
2. 阶段 4 的实验 14 最后选了必须有 RenderingDevice 的路（计算着色器，或者和 Skia 共享 GPU）。

**方向里"让 Skia GPU 在 Godot 里共享上下文"那个实验**：我把它降成有条件才做，而且只考虑 RenderingDevice。Compatibility 下不做：Godot 自己缓存了 GL 状态又不给重置的接口，外来的 GL 调用每次都得把状态原样摆回去，引擎一升级就可能坏。

#### Cocos Creator 3.8.x，H5

mac 做好后才开始，开始前先过实验 15。现在能定的：

- **内核**编成 WASM（Emscripten）。不依赖 SharedArrayBuffer：主线程一份内核做求值和调度，若干 Web Worker 各一份只做栅格化，结果用可转移的 ArrayBuffer 送回，零拷贝。
- **组件** `SvgSprite`，继承 `UIRenderer`，自定义顶点组装，把合成指令填成四边形。做法参考 Cocos 的 Spine 组件。
- **纹理上传**走 gfx 的 `copyBuffersToTexture`，它带区域参数，H5 上可以局部更新（细节在实验 15 核实）。
- **混合**：Cocos 的材质可以自定混合因子，滤色一遍就行。
- **离屏**：RenderTexture。你允许改引擎，所以需要时可以在 2D 渲染流程里加一个执行离屏通道的钩子，不用绕。
- **计算着色器不指望**：Cocos 3.8 的计算着色器只在 Vulkan、Metal、GLES 3.1 上有，WebGL 和 WebGL2 没有，而且只能在自定义管线里用。
- **体积**：wasm 压缩后 1.5 MB 以内是我的目标，阶段 0 试编时量。

## 6 分层规则和每帧调度

### 6.1 五种层

| 层 | 什么时候用 | 缓存 | 每帧做什么 |
|---|---|---|---|
| **不变层** | 内容永远不变 | 画一次；同素材所有实例共用 | 只合成 |
| **移动层** | 只有变换、透明度在变 | 画一次；共用 | 改矩阵和透明度 |
| **染色层** | 颜色由代码给，或只有整体颜色在变 | 画一次（单通道，或两张图） | 改着色器里的颜色 |
| **重画层** | 形状、渐变、虚线、文字排布等内容在变 | 小的循环存一整圈；大的每次重画 | 在预算内重画并上传 |
| **离屏组** | 组透明度、滤镜、遮罩、混合模式，而且里面有各自在动的东西 | 子层各自缓存；组的结果每次重算 | 把子层合成一次，再做整体效果 |

滤镜不单独算一种层：内容和参数都不变时，滤镜结果直接烤进所在的层；有东西在变时，就是一个带滤镜的离屏组。

### 6.2 编译时怎么分层

1. **给每个节点定"会怎么变"**（所有动作合起来看）：不变 / 只动变换和透明度 / 只动整体颜色 / 内容变 / 效果参数变。
2. **按画的顺序走一遍**：
   - 连续的不变内容并成一个不变层；
   - 遇到只动变换或透明度的节点，它的子树单独成一个移动层（里面还有会动的，就再嵌一层）；
   - 内容会变的节点成重画层；
   - 带组效果的节点，按 6.3 判断是烤进缓存、分给子层，还是成为离屏组。
3. **合并**：两个不变层中间夹着一个移动层时，如果移动层在所有动作、所有时刻的包围盒都碰不到它们，就把两个不变层并成一个。这一步减层数、减重叠绘制。
4. **给每层算**：各动作下随时间的包围盒并集；能不能降分辨率；是不是完全不透明；是不是只有一种颜色。

**能不能降分辨率**的规则：层里所有内容都经过了半径（σ）不小于 3 像素的模糊，就可以用一半分辨率存；不小于 6 像素可以用四分之一。编译器按这个规则定了以后，用降了分辨率的缓存再画一遍和参照比，过不了线就退回全分辨率。

### 6.3 各种情况怎么处理

对应方向 4.1 的表，逐条给决定。

| 情况 | 决定 |
|---|---|
| 静态子树 | 不变层 |
| 只动变换、透明度 | 移动层。缓存按"倍率档"存（6.4）。放大超出当前档就按新档重画。**停下来 0.2 秒后**，如果停住的姿势不是原样（比如播完停在转了 10 度的位置），按停住的姿势重画一张清晰的 |
| currentColor 染色 | 编译器自动判断走哪条路，按便宜到贵排：① 层里全是 currentColor 的纯色 → **单色染色**，存单通道，显存只要四分之一；② 层的结果对染色颜色是"线性"的 → **双图染色**：染成黑、染成白各存一张，任意颜色在着色器里按比例混出来；③ 其他 → 按颜色重画，颜色进缓存键。怎么判断是不是"线性"：编译时再用第三种颜色画一张，和黑白两张混出来的比，过静止帧的线就是 |
| 整体颜色动画（纯色形状的颜色在变） | 同上的 ① 或 ②，颜色由时间线给 |
| 颜色矩阵 | "颜色矩阵"着色器 |
| 路径形变、渐变停靠点动画、虚线偏移、沿路径排的文字在滚 | 重画层 |
| 滤镜 | 内容和参数都不变：烤进缓存，柔和的降分辨率。有变化：离屏组，阶段 2 用 CPU 重算（可以降到每秒 15–30 次），阶段 4 换成 GPU 通道 |
| 遮罩、裁剪在动 | 内容一层，遮罩一层（单通道），合成时用"遮罩相乘"着色器。多重嵌套且都在动：离屏组。矩形裁剪（`clip-path: inset()`）在动：只是"矩形裁剪"着色器的参数，不用遮罩纹理 |
| **混合模式，素材内部** | 整块 SVG 是一个隔离组，这是 Chrome 的实际语义（最外层的 svg 元素本来就自成一组）。混合只和**同一素材里**下面的内容发生。下面的内容和自己都不变：混合结果烤进缓存，运行时零成本。否则：离屏组 |
| **混合模式，跨素材** | 是**实例的参数**（`set_blend`），不是文件内部的事。约定：SVG 根元素上写的 `mix-blend-mode` 当作这个素材的默认值。支持普通、相加、相乘、滤色四种，都不用读屏幕。其他模式跨素材这一版不支持：它们必须读背景，Godot 里要拷屏幕，贵而且个数有限 |
| 组透明度，子层各自在动 | 编译时检查子层随时间的包围盒：互相碰不到 → 把透明度分给各子层，零成本；会重叠 → 离屏组 |
| 组滤镜，里面有东西在动 | 离屏组 |
| 文字 | 字形轮廓是共用子图，跟普通形状一样进层。沿路径滚动的文字是重画层 |
| 同一个渐变或 pattern 被很多元素引用 | 资源表里只有一份；画的时候 pattern 的瓦片只录一次 |

**离屏组怎么执行**：

- **CPU 版**（阶段 2，哪里都能跑）：这类组的子层除了上传到 GPU，还各留一份内存里的位图。工作线程用 Skia 按当前的变换把它们合起来，做滤镜或混合，结果当一个重画层上传。
- **GPU 版**（阶段 4）：内核把要做的事排成通道列表，接入层用引擎的离屏能力执行（Godot 用 DrawableTexture，Cocos 用 RenderTexture）。子层不用再留内存位图。

### 6.4 缓存：键、倍率档、共用

- **缓存键**：（素材指纹，层号，倍率档，颜色——只有"按颜色重画"的层才有，内容时刻——只有重画层才有）。
- **倍率档**：相邻两档差 √2 倍（…、0.5、0.71、1、1.41、2、…）。需要的倍率 = 实例缩放 × 层内动画的缩放 × 设备倍率，向上取到最近的档。所以缓存总是被缩小着用，最多缩到 0.71，不放大。动画过程中允许临时放大到 1.25 倍，再大就重画。
- **缓存倍率系数**默认 1.0，也就是缓存的分辨率正好等于屏幕上的分辨率。这和 Chrome 播动画时的做法一样，发软程度也就和它一样。档距和系数最终由实验 9 定。
- **停在两档之间的实例**（比如一直以 0.8 倍显示）：**按实际倍率重画，静止画面按静止帧的线验收。** 理由：倍率档是给"正在动"准备的；一张牌一直以 0.8 倍摆在桌上，如果永远用 1 倍的缓存缩着画，它就永远是软的，这不能算"和 Chrome 一样"。规则：
  - 实例的缩放和旋转连续 0.2 秒没变，就给它的各层按**实际的倍率和转角**各画一张"定稿缓存"，画好后替换掉按档取的那张。和 6.3 里"移动层停下来后按停住的姿势重画"是同一条规则，只是把实例自己的缩放和旋转也算进去。
  - 定稿缓存的键是（素材，层，实际倍率，转角）。倍率和转角相同的实例照样共用——同一排牌都是 0.8 倍，只画一份。
  - 位置的小数部分不进键。接入层默认把静止实例的位置对齐到整像素（可关）；关掉以后，静止但没对齐的实例按运动中的线算。
  - 实例一动，立刻退回按档取的缓存；定稿缓存留着，停回同样的倍率时直接用。
  - **有上限**：每个层最多留 4 张定稿缓存（可配），最久没用的先淘汰。同一素材同时有 4 种以上不同的静止倍率时，多出来的继续用按档的缓存，统计里记成"没定稿的静止实例"。这个数不为 0 时，那些实例只保证运动中的线。
  - 显存：定稿缓存比按档的那张小（0.8 倍的面积是 1 倍的 64%），定稿后那一档如果没有别的实例在用，可以淘汰，所以通常是省显存的。
- **共用**：同素材的实例共用不变层、移动层、染色层。倍率不同的实例各用各的档。
- **重画层的共用**：
  - **整圈缓存**：循环的重画层，如果"一圈的帧数 × 面积 × 4 字节"不超过每层上限（默认 4 MB），就把一整圈都存下来。之后不再重画，实例从哪一刻开始播都能共用。
  - **分组**：存不下一整圈的，同素材的实例按循环进度分成 4 组，同组共用一张图。
- **图集**：边长不超过 256 的层进图集页（1024×1024，一页 4 MB；单通道的层进单通道的页，一页 1 MB）。大的用独立纹理。任一边超过 2048 的切成 512×512 的瓦片，只画视口内和外面一圈。
- **图集里每块四周留 2 像素透明边**，防止双线性取样串到邻居。

### 6.5 每帧调度

```
1. 时钟前进。对视口内的实例求时间线。
   同素材、同动作、同进度的实例只算一次。

2. 对每个实例的每一层：
   a. 算需要的倍率，取档；
   b. 找缓存。有 → 用。没有 → 排一个栅格化任务；这一帧先用别的档顶一下，
      连别的档也没有，按"没备好时怎么办"的设定处理；
   c. 移动层：只更新矩阵和透明度；如果倍率超档或者刚停稳，排一个低优先级的重画任务；
   d. 重画层：排下一帧要用的那张（提前一帧画）。

3. 任务按优先级派给工作线程，总量不超过"每帧栅格化预算"：
   屏幕上的重画层 > 屏幕上还没缓存的 > 升级重画 > 预热

4. 收已经画完的结果，在"每帧上传预算"内上传，超出的留到下一帧。

5. 按实例顺序、层顺序生成合成指令。

6. 记统计。显存超预算就淘汰。
```

**没备好时怎么办**：默认是整个实例等所有层齐了再显示，并发"备好了"的信号，避免东一块西一块地冒出来。可选"先糊后清"：先用四分之一倍率画一张顶上。场景切换用 `prewarm` 提前准备，配合加载画面。

**主线程的时间目标**（M3）：求值加调度不超过 1.5 毫秒，上传不超过 2 毫秒，接入层提交不超过 1.5 毫秒。

### 6.6 预算和降级

**默认预算**：

| 项 | mac（Godot） | H5 桌面浏览器 | H5 手机浏览器 |
|---|---|---|---|
| 显存（缓存纹理合计） | 384 MB | 256 MB | 96 MB |
| 每帧栅格化 | 工作线程合计 4 毫秒的墙上时间 | 同左 | 6 毫秒 |
| 每帧上传 | 8 MB | 8 MB | 4 MB |
| 工作线程 | 核数 − 2，最多 6 | 最多 4 个 Worker | 最多 2 个 Worker |
| 每层整圈缓存上限 | 4 MB | 4 MB | 2 MB |

**降级的控制办法**（借自 three.js 那个例子，它的参数调得很稳）：

- 看最近一段（至少 45 帧或 0.9 秒）的平均帧时间；
- 超过 21.5 毫秒：降一级；
- 低于 17.4 毫秒并且等够了时间：升一级；
- 每次降级后，下次升级前要等的时间翻倍（从 4 秒起，最长 60 秒），防止来回抖。

**降级的级别**，从轻到重：

| 级别 | 做什么 | 画面影响 |
|---|---|---|
| 0 | 正常 | 无 |
| 1 | 更多柔和的层降分辨率 | 几乎看不出 |
| 2 | 重画层和离屏组降到每秒 30 次 | 变形动画略不顺 |
| 3 | 重画层分辨率降到 0.71 倍 | 变形的部分略糊 |
| 4 | 每秒 20 次，分辨率 0.5 倍 | 明显 |
| 5 | 屏幕外的、屏幕上很小的重画层停止更新 | 小东西不动了 |
| 6 | 所有缓存的倍率整体降到 0.85，再到 0.7 | **已经不保证和 Chrome 一样**。默认关，游戏自己决定开不开 |

方向里的顺序是"柔和层降分辨率 → 动态层降帧率 → 动态层降分辨率 → 烤成帧"。前三步我保留。"烤成帧"我拆成了两件事：运行时的"整圈缓存"是常规手段，不算降级；编译时把一段动画烤成位图放进包里，和"包里存矢量"相反，这一版**不做**，文件格式里留了位置。哪个素材在基准机上到了 4 级以上，素材检查工具会点名，由人决定是改美术还是以后加烤帧。

**显存超预算时的淘汰顺序**：屏幕外的高倍率档 → 屏幕外的素材 → 整圈缓存 → 屏幕上的高倍率档换成低一档。

每次降级都计数，统计里看得到。**跑对照测试时降级次数必须是 0。**

## 8 方向第 7 节十个问题的决定

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| 1 | 参照用 CPU 还是 GPU 光栅 | **CPU**，而且用"冻结图"。GPU 只用来量 Chrome 自己的差 | 本机实测：CPU 下截图逐字节可重复；Chrome 自己 CPU 对 GPU 的相似度在细线多的图上只有 0.987，拿 GPU 当参照就定不出线。同意方向的倾向 |
| 2 | 光栅内核 | **Skia CPU**，锁 Chrome 的提交。不留 ThorVG 备选 | 见 5.4。上限 10 MB 够用；ThorVG 的滤镜只有模糊 |
| 3 | 动画哪些运行时算，哪些采样 | 支持表里的都在运行时算。**编译时逐轨和 Chrome 每 20 毫秒对一次，对不上的自动换成采样轨**，并在报告里记下来 | 这样不用事先争论"哪些算冷门"：算得对的就算，算不对的自动兜底，两种都被同一个检查盖住。同意方向的倾向，把"冷门"的界线改成了由检查自动划 |
| 4 | 重采样误差上限、重画阈值、缓存倍率 | 起步：运动中相似度 1 倍 ≥ 0.975、2 倍 ≥ 0.985；倍率档差 √2；缓存倍率系数 1.0；停下 0.2 秒重画。最终由实验 9 定 | 标尺用 Chrome 自己：它播动画时也是缓存层再变换，本机量到它自己的活图对冻结图是 0.964–0.998。我们不需要比它更清晰 |
| 5 | 混合模式和隔离组 | 整块 SVG 是一个隔离组；素材内的混合能烤就烤，否则离屏组；跨素材的混合是实例参数，支持普通、相加、相乘、滤色 | 这正是 Chrome 的语义。四种跨素材模式都能用固定的混合方式做，不读屏幕。同意方向的倾向，补了"哪几种"和"怎么做" |
| 6 | 文字 | 写死的文字：**编译时转成字形轮廓**，位置由 Chrome 定，运行时当路径画。代码填的文字交给引擎 | 比方向的倾向（运行时做字形缓存）更简单：不用带字体引擎，省体积；各平台画出来一样；文字和别的形状走同一套分层和缓存。代价是文字边缘和 Chrome 的字形光栅会有细微差别，所以文字区域单独一条线（0.98）。实验 6 先证明这条线过得了；过不了再回到方向的方案 |
| 7 | 中间格式 | 一个素材一个文件；索引段直接读，数据段按层解码；不做网络流式；默认量化到 1/64 单位；文件本身不压缩 | 素材文件很小，流式没有收益。同意方向的倾向，把"内存映射"和"量化压缩"的矛盾用"索引段、数据段分开"解决了 |
| 8 | 显存预算和降级顺序 | 预算见 6.6 的表。顺序：柔和层降分辨率 → 重画层降帧率 → 降分辨率 → 停更小的和屏外的 →（可选）整体降倍率。"编译时烤成帧"这一版不做 | 见 6.6 |
| 9 | 由代码控制的参数 | 沿用并推广成素材清单里的五样：动作（三种触发方式）、染色、槽、开关、锚点和打击点 | 现有约定都能一对一转过来。新增"开关"和"SMIL 触发"。同意方向的倾向 |
| 10 | Godot 先做哪个渲染器 | 先 Compatibility。同一份接入代码在 Mobile / Forward+ 上也要过引擎内对照。GPU 部分用两边都有的 DrawableTexture | 游戏现在就用 Compatibility。方向说"GPU 动态层在 Mobile 上做"，我改了：4.7 的 DrawableTexture 让两种渲染器走同一条路，不必分开 |

## 12 three.js 那个参考（《几猫3A大作》）

只读了源码，没有运行（微信收到的文件）。它是一个把 three.js r180 打包进去的单文件 3D 游戏，1.4 MB，没有任何图片。

**可以借的，已经写进设计**：

| 它的做法 | 我们对应的地方 |
|---|---|
| 包里只放"配方"（着色器函数、建模代码），不放图 | 包里放 `.svgbin` |
| 启动时按设备档位（贴图边长 512–2048）在 GPU 上把材质烤成贴图，之后当普通贴图用 | 分层缓存和倍率档；5.4 和阶段 4 里"滤镜尽量在 GPU 上烤" |
| 总像素有上限；按帧时间自动调渲染倍率（最低 0.6），到底了再自动降一档画质；回升的等待时间翻倍 | 6.6 的降级控制办法，参数直接借用 |
| 启动时看 GPU 型号定初始档位 | H5 那一档的初始预算（做 Cocos 时用） |
| 实例化、合并几何、共用材质 | 同素材共用缓存、图集合批 |

**搬不过来的**：

1. **美术的来源不同。** 它的美术是程序写的，长什么样代码自己说了算，没有"和某个参照一样"的要求。我们的输入是美术画的 SVG 加 CSS / SMIL 动画，要和 Chrome 一样。
2. **每帧全画不适合丰富的 SVG。** 它是 3D 场景，不透明物体靠深度缓冲，一个像素基本只算一次。SVG 是大量半透明的图形按顺序叠，还带滤镜、遮罩、混合，每帧全画的账方向 3.2 已经算过。
3. **抗锯齿。** 它用多重采样（0–4 倍）。Chrome 画 SVG 的边是按面积精确算的，4 倍多重采样画细线和小图形差得明显，过不了 0.995。

**它启发的一个新实验**（并进实验 14）：大面积、形状少的平涂层（比如背景里的大色块），存成贴图很占显存，直接用几何画反而便宜。可以试"边缘存一条窄带的覆盖率，内部用纯色矩形填"，显存跟周长走而不是跟面积走。这是优化，不在前三个阶段里。
